# 22. 번들러와 빌드 — 왜 빌드가 필요한가

> **이 장의 질문**: 브라우저는 JavaScript를 실행하는데, 왜 JavaScript를 빌드해야 하는가?

## BE로 치면 이런 것

Kotlin 코드는 그대로 실행되지 않습니다. 컴파일해서 바이트코드로 바꾸고, 의존성과 함께 JAR로 묶어야 JVM이 돌립니다. `./gradlew build`가 하는 일이죠.

프론트엔드도 같습니다. 다만 **묶는 이유가 다릅니다.**

| | 백엔드 | 프론트엔드 |
| --- | --- | --- |
| 왜 컴파일 | JVM이 소스를 못 읽음 | 브라우저가 TS·JSX를 못 읽음 |
| 왜 묶음 | 배포 단위를 하나로 | **네트워크로 보내야 하니까** |

두 번째가 결정적입니다. 백엔드 JAR이 50MB여도 서버에 한 번 올리면 그만이지만, **프론트엔드 결과물은 사용자가 접속할 때마다 회선으로 내려갑니다.** 그래서 프론트엔드 빌드는 "돌아가게 만들기"보다 **"작게 만들기"** 에 더 많은 노력을 씁니다.

## 빌드가 없으면 벌어지는 일

빌드 없이 소스를 그대로 브라우저에 준다고 해봅시다. 네 가지가 막힙니다.

### 1. 브라우저가 못 읽는 문법

```tsx
const rows: Order[] = data.map(o => <Row key={o.id} order={o} />);
```

브라우저에게 이것은 문법 오류입니다. `: Order[]`도 모르고 `<Row />`도 모릅니다. **TypeScript와 JSX는 브라우저 문법이 아닙니다.**

### 2. 구형 브라우저가 못 읽는 최신 문법

`?.`, `??`, 최신 문법들은 오래된 브라우저에서 안 돕니다. 회사 정책으로 브라우저가 고정된 사용자가 있다면 실제 문제입니다.

### 3. 파일이 너무 많다

컴포넌트 200개면 파일 200개입니다. 여기에 `node_modules`의 패키지들이 더해집니다. 브라우저가 이걸 하나씩 요청하면 **요청이 수천 개** 가 됩니다(3장의 워터폴).

### 4. 아무도 안 쓰는 코드까지 간다

라이브러리에서 함수 하나만 썼는데 라이브러리 전체가 사용자에게 갑니다.

## 빌드가 하는 일

```
소스 (TS, JSX, CSS, 이미지)
   │
   ├─ ① 트랜스파일   TS/JSX → 브라우저가 읽는 JS
   ├─ ② 번들         수백 개 파일 → 몇 개로 묶기
   ├─ ③ 트리 셰이킹  안 쓰는 코드 잘라내기
   ├─ ④ 코드 스플리팅 필요할 때 받도록 쪼개기
   ├─ ⑤ 최소화       공백·주석 제거, 이름 줄이기
   └─ ⑥ 소스맵       디버깅용 지도 만들기
   │
결과물 (브라우저용 JS/CSS 몇 개)
```

하나씩 봅니다.

### ① 트랜스파일 — 문법 변환

TypeScript를 JavaScript로, JSX를 함수 호출로, 최신 문법을 구형 문법으로 바꿉니다. 이 일을 하는 도구가 Babel, SWC, esbuild 같은 것들입니다.

**중요한 점**: 트랜스파일은 **타입 검사가 아닙니다.** 요즘 도구들은 타입 표기를 그냥 **지워버리고** 넘어갑니다. 그게 훨씬 빠르니까요.

> **그래서 실무 규칙이 하나 나옵니다.** 빌드가 통과했다고 타입이 맞는 게 아닙니다. **타입 검사(`tsc --noEmit`)는 별도로 돌려야 합니다.** CI에 이게 빠져 있으면 타입 에러가 그대로 배포됩니다(23장).

### ② 번들 — 묶기

진입점(예: `main.tsx`)에서 시작해 `import`를 따라가며 필요한 파일을 전부 찾아내고, 하나의 파일로 이어 붙입니다. 이 의존성 지도를 **모듈 그래프** 라고 부릅니다.

### ③ 트리 셰이킹 — 안 쓰는 코드 자르기

```js
import { formatDate } from 'date-utils';   // 이 라이브러리에 함수가 50개 있어도
```

실제로 쓴 `formatDate`와 그것이 부르는 것만 남기고 나머지는 버립니다. ProGuard가 하는 일과 같은 발상입니다.

**항상 되는 건 아닙니다.** 조건이 있습니다.

- **ESM(`import`/`export`)으로 작성된 패키지여야 합니다.** 옛 CommonJS(`require`)는 정적 분석이 어려워 잘 안 잘립니다
- 모듈을 불러오는 것만으로 뭔가 일어나는 코드(부수 효과)가 있으면 함부로 못 자릅니다

> 그래서 같은 기능이라도 **ESM으로 배포하는 최신 라이브러리** 를 고르는 게 번들 크기에 유리합니다(21장의 선택 기준).

### ④ 코드 스플리팅 — 나눠서 받기

전부 한 파일로 묶으면 첫 화면에서 앱 전체를 내려받게 됩니다. 관리자 대시보드에 화면이 30개인데 사용자는 목록 하나만 보고 나갈 수도 있는데 말이죠.

```tsx
// 이 컴포넌트는 실제로 필요해질 때 별도 파일로 내려받는다
const ReportPage = lazy(() => import('./ReportPage'));
```

`import()` 를 **함수처럼 호출** 하면 번들러가 거기를 분리 지점으로 잡습니다. Next.js는 페이지 단위로 이걸 자동으로 해줍니다(30장).

### ⑤ 최소화

공백과 주석을 지우고, 지역 변수 이름을 짧게 바꿉니다. `calculateTotalAmount` → `a`. 여기에 서버의 gzip/brotli 압축이 더해지면 전송량이 크게 줄어듭니다.

### ⑥ 소스맵

⑤를 거치면 사람이 읽을 수 없는 코드가 됩니다. 에러가 나면 `a.js:1:24839` 같은 위치만 나오죠. **소스맵은 그 위치를 원래 소스의 파일·줄로 되돌려주는 지도** 입니다. 디버그 심볼과 같은 역할입니다.

> 프로덕션에 소스맵을 공개할지는 판단이 필요합니다. 공개하면 누구나 원본 코드를 읽을 수 있고, 안 하면 에러 추적 도구가 위치를 못 짚습니다. **에러 추적 서비스에만 따로 올리는 것** 이 흔한 절충입니다.

## 개발 서버 — 빌드를 기다리지 않기

위 과정을 저장할 때마다 다 하면 너무 느립니다. 그래서 개발할 때는 다르게 동작합니다.

**HMR(Hot Module Replacement)** — 파일 하나를 고치면 **그 모듈만 갈아끼우고** 화면은 그대로 둡니다. 페이지가 새로고침되지 않아서, 입력하던 값이나 열어둔 모달이 유지됩니다.

백엔드의 자동 리로드와 비슷한데, 차이가 하나 있습니다. 서버 리로드는 상태가 어차피 요청마다 사라지지만(2장), **프론트엔드는 살아 있는 상태를 유지한 채 코드만 바꿔치기합니다.**

## 도구 지형

| 도구 | 성격 |
| --- | --- |
| **webpack** | 오랜 표준. 설정이 강력하지만 복잡하고 느림 |
| **Vite** | 요즘 기본 선택. 개발 중에는 번들하지 않아 매우 빠름 |
| **esbuild / SWC** | Go·Rust로 만든 초고속 변환기. 다른 도구의 내부 엔진으로 쓰임 |
| **Turbopack** | Next.js가 쓰는 번들러 |

**대부분의 경우 이 설정을 직접 만질 일이 없습니다.** Next.js 같은 프레임워크가 합리적인 기본값을 제공하기 때문입니다. 이름과 역할만 알아두고, 빌드가 깨졌을 때 에러 메시지의 출처를 짐작할 수 있으면 충분합니다.

## 번들 크기를 실제로 확인하기

추측하지 말고 재는 것이 원칙입니다.

```bash
npx next build          # 라우트별 크기를 표로 출력
npx vite build          # 청크별 크기 출력
```

빌드 결과에 파일별 크기가 나옵니다. **어느 화면이 왜 무거운지** 를 시각화해주는 번들 분석 도구도 있습니다. 대개 범인은 하나입니다 — 크고 무거운 라이브러리를 첫 화면에서 불러오는 것.

> 자주 쓰이는 기준: 첫 화면에서 내려받는 JS를 **압축 후 200KB 이하** 로 잡습니다. 절대 규칙은 아니지만, 이 선을 크게 넘기면 느린 회선에서 체감이 확 나빠집니다. 재는 방법은 24장에서 다룹니다.

## 환경변수

빌드 시점에 값이 코드 안으로 박힙니다. 10장에서 봤듯 **`NEXT_PUBLIC_` 접두사가 붙은 것을 클라이언트 코드에서 참조하면 그 값이 결과물에 문자열로 들어갑니다.**

여기서 실무에서 자주 겪는 함정 하나. **환경변수를 바꾸면 다시 빌드해야 합니다.** 서버 애플리케이션처럼 재시작만으로 반영되지 않습니다. 이미 만들어진 파일 안에 값이 박혀 있으니까요.

## 흔한 오해

**"빌드가 통과했으니 타입은 맞다"**
아닙니다. 대부분의 번들러는 타입을 검사하지 않고 지웁니다. `tsc --noEmit`을 따로 돌리세요.

**"번들은 작을수록 좋다"**
방향은 맞지만 **첫 화면에 필요한 것** 이 작아야 한다는 뜻입니다. 전체 합계를 줄이려고 지연 로딩을 남발하면 화면 전환마다 기다리게 됩니다.

**"트리 셰이킹이 알아서 다 잘라준다"**
ESM으로 배포된 패키지여야 하고, 부수 효과가 없어야 합니다. 안 잘리는 라이브러리가 실제로 많습니다.

**"webpack 설정을 배워야 한다"**
프레임워크를 쓰면 거의 만질 일이 없습니다. 필요해질 때 배우세요.

## 핵심 3가지

- **빌드는 두 가지를 합니다.** 브라우저가 못 읽는 문법을 바꾸고(트랜스파일), 네트워크로 보내기 좋게 묶고 줄입니다(번들·트리 셰이킹·스플리팅).
- **타입 검사는 빌드에 포함되지 않습니다.** 번들러는 타입을 지울 뿐입니다. `tsc --noEmit`을 따로 돌려야 합니다.
- **결과물은 사용자 회선으로 갑니다.** 그래서 번들 크기가 성능 지표가 되고, 라이브러리 선택이 사용자 경험에 직접 영향을 줍니다.
