# 23. 린트 · 테스트 · CI · 배포

> **이 장의 질문**: 프론트엔드 변경을 무엇으로 검증하고, 배포한 뒤에는 무엇을 더 신경 써야 하는가?

## 문제 상황

PR이 하나 올라왔습니다. 빌드도 통과했고 화면도 잘 뜹니다. 그런데 머지하고 배포한 다음 이런 제보가 옵니다.

- "목록에서 행을 눌러도 상세가 안 열려요"
- "어제까지 되던 화면에서 갑자기 에러가 나요"

빌드는 **문법이 맞는지** 만 봤습니다. **동작이 맞는지** 는 아무도 안 봤고, **어제 코드를 들고 있는 사용자** 도 아무도 신경 쓰지 않았습니다.

이 장은 그 두 구멍을 메우는 이야기입니다.

## BE로 치면 이런 것

당신의 파이프라인은 대략 이럴 겁니다.

```
커밋 → 컴파일 → 정적 분석 → 단위 테스트 → 통합 테스트 → 빌드 → 배포
```

프론트엔드도 모양은 같습니다. 다른 것은 **각 단계에서 무엇을 검사하느냐**, 그리고 **배포 이후에 벌어지는 일** 입니다.

## 정적 검사 — 세 가지를 구분하기

프론트엔드에는 역할이 다른 도구가 셋 있고, 초보자가 자주 뭉뚱그립니다.

| 도구 | 무엇을 보나 | 못 고치면 |
| --- | --- | --- |
| **TypeScript** (`tsc --noEmit`) | 타입이 맞는가 | 런타임 에러 |
| **ESLint** | 위험하거나 잘못된 패턴인가 | 버그 |
| **Prettier** | 보기 좋게 정렬됐는가 | 아무 일도 안 남 |

**셋의 성격이 완전히 다릅니다.**

- **Prettier는 스타일만** 봅니다. 들여쓰기, 따옴표, 줄바꿈. **코드의 의미를 전혀 모릅니다.** 그래서 논쟁할 가치가 없고, 저장할 때 자동으로 돌리면 끝입니다
- **ESLint는 의미를 봅니다.** "`useEffect`의 의존성이 빠졌다", "`==`를 썼다", "선언만 하고 안 쓴 변수가 있다" 같은 것들
- **TypeScript는 타입을 봅니다.** 22장에서 봤듯 **빌드에 포함되지 않으므로 반드시 별도로 돌려야 합니다**

React 프로젝트에서 특히 중요한 ESLint 규칙은 이것입니다.

```
react-hooks/rules-of-hooks       훅을 조건문 안에서 부르지 않았는가 (19장)
react-hooks/exhaustive-deps      의존성 배열에 빠진 것이 없는가 (19장)
```

19장에서 "린터가 잡아준다"고 한 것이 이 규칙들입니다. **경고를 주석으로 끄지 마세요.** 대부분 진짜 버그입니다.

## 테스트 — 무엇을 테스트할 것인가

여기가 백엔드와 가장 크게 갈리는 지점입니다.

백엔드에서는 대체로 **입력 → 출력** 이 명확합니다. 함수에 값을 넣고 반환값을 보면 됩니다. 프론트엔드에서 테스트하려는 것은 대개 **"사용자가 이렇게 하면 화면이 저렇게 된다"** 입니다.

### 세 층

```
        E2E              적음. 느림. 진짜 브라우저에서 시나리오 전체
      ─────────
    컴포넌트 테스트       중간. 이 층이 가장 값어치가 큽니다
    ─────────────
   단위 테스트            많음. 빠름. 순수 함수만
```

**백엔드와 비율이 다릅니다.** 백엔드는 단위 테스트가 두터운데, 프론트엔드에서는 **컴포넌트 테스트가 중심** 입니다. 순수 함수로 뽑아낼 만한 로직이 상대적으로 적고, 버그는 대개 "상태와 화면이 어긋나는" 지점에서 나기 때문입니다.

### 단위 테스트 — 순수 함수만

```ts
// 금액 포맷 같은 것. 화면과 무관하고 입출력이 명확하다
test('천 단위 구분자를 넣는다', () => {
  expect(formatAmount(1234567)).toBe('1,234,567');
});
```

도구는 **Vitest** 나 **Jest** 입니다. JUnit 자리라고 보면 됩니다.

### 컴포넌트 테스트 — 사용자처럼 다루기

```tsx
// render   — 컴포넌트를 가상 화면에 그린다
// screen   — 그려진 화면에서 요소를 찾는다
// userEvent— 진짜 사용자처럼 클릭·입력한다
// vi.fn()  — 호출 기록을 남기는 가짜 함수 (Jest에서는 jest.fn())

test('행을 클릭하면 선택한 주문 ID를 부모에게 전달한다', async () => {
  const handleSelect = vi.fn();
  render(<OrderTable orders={[{ id: 'ORD-1', status: 'PAID' }]} onSelect={handleSelect} />);

  await userEvent.click(screen.getByRole('button', { name: 'ORD-1' }));

  expect(handleSelect).toHaveBeenCalledWith('ORD-1');
});
```

**Testing Library** 를 씁니다. 이 도구의 철학이 중요합니다.

> **테스트는 사용자가 화면을 인식하는 방식으로 요소를 찾아야 한다.**

그래서 CSS 클래스나 컴포넌트 내부가 아니라 **역할(role)과 이름** 으로 찾습니다. `getByRole('button', { name: 'ORD-1' })`처럼요.

이 규칙에는 큰 부수 효과가 있습니다. **12장에서 시맨틱 태그를 제대로 쓴 화면은 테스트도 쉽게 써집니다.** `<div onClick>`으로 만든 버튼은 `getByRole('button')`으로 잡히지 않습니다. 접근성과 테스트 가능성이 같은 방향을 봅니다.

### 무엇을 테스트하지 말아야 하는가

프론트엔드에서 가장 흔한 낭비입니다.

```tsx
// ❌ 구현 세부를 테스트한다. 리팩터링만 해도 깨진다.
expect(wrapper.find('.order-row').length).toBe(3);
expect(component.state.isLoading).toBe(true);
```

```tsx
// ✅ 사용자가 보는 것을 테스트한다.
expect(screen.getAllByRole('row')).toHaveLength(4);   // 헤더 포함
expect(screen.getByText('불러오는 중')).toBeVisible();
```

**기준**: 그 테스트가 깨졌을 때 **사용자에게 실제로 문제가 생긴 것인가?** 아니라면 그 테스트는 리팩터링을 방해할 뿐입니다.

### E2E — 진짜 브라우저에서

**Playwright** 나 Cypress로 실제 브라우저를 띄워 시나리오를 돌립니다. 로그인 → 목록 → 상세 → 수정 → 저장 같은 흐름이죠.

느리고 잘 깨집니다. 그래서 **핵심 경로 몇 개만** 두는 것이 맞습니다. 백엔드의 통합 테스트와 같은 감각입니다.

## CI 파이프라인

```yaml
# 개념적인 순서. 앞의 빠른 단계에서 먼저 걸러낸다.
1. 의존성 설치       pnpm install --frozen-lockfile   ← 락 파일 그대로 (21장)
2. 포맷 검사         prettier --check
3. 린트              eslint .
4. 타입 검사         tsc --noEmit                     ← 빌드보다 훨씬 빠릅니다 (22장)
5. 테스트            vitest run
6. 빌드              next build
7. E2E               playwright test
```

**순서에 원칙이 있습니다. 빠르고 흔한 실패를 앞에 둡니다.** 타입 에러 때문에 E2E까지 다 돌린 뒤 실패하면 시간 낭비니까요.

**4번을 빼먹지 마세요.** `next build`가 타입 검사를 포함하기는 하지만(22장), 그건 6번입니다. **타입 에러 하나 때문에 빌드 전체를 기다릴 이유가 없습니다.** 변환기만 쓰는 구성이라면 이 줄이 유일한 타입 검사이기도 합니다.

## 배포 — 대부분 서버가 필요 없다

**브라우저에서만 도는 앱** 이라면, 빌드 결과물은 **그냥 파일** 입니다. HTML, JS, CSS, 이미지. 실행할 프로세스가 없습니다.

그래서 배포가 "파일을 어디에 올려두는 일"이 됩니다.

```
빌드 결과물 → 정적 호스팅 → CDN이 전 세계에 복제 → 사용자는 가까운 곳에서 받음
```

Vercel, Netlify, S3+CloudFront 같은 것들이 이 자리입니다. 서버 관리도, 오토스케일링도 없습니다.

> **Next.js는 기본적으로 서버가 도는 쪽입니다.** 조건을 맞추면 정적 파일로만 내보낼 수도 있지만, 일반적인 빌드에는 서버에서 실행되는 부분이 포함됩니다. 자세한 것은 Part 7(28장부터)에서 다룹니다. 다만 **JS·CSS·이미지 같은 정적 파일이 CDN에서 나간다는 구조는 어느 쪽이든 그대로** 입니다.

### 프리뷰 배포

프론트엔드 배포 도구들이 기본으로 제공하는 기능인데, 실무 영향이 큽니다.

**PR을 열면 그 브랜치만의 URL이 자동으로 생깁니다.** 리뷰어가 코드를 읽는 대신 **실제 화면을 눌러볼 수 있습니다.** 기획자나 디자이너도요.

백엔드에서 브랜치마다 환경을 띄우려면 큰일이지만, 정적 파일은 그냥 다른 폴더에 올려두면 그만이라 공짜에 가깝습니다.

## 배포 후 — 백엔드에 없는 문제

2장에서 예고했던 것을 여기서 회수합니다.

> **배포해도 이미 접속해 있는 사용자는 옛 코드를 들고 있습니다.**

백엔드는 배포하면 다음 요청부터 새 코드입니다. 프론트엔드는 **사용자가 새로고침할 때까지** 몇 시간이고 옛 코드가 돕니다(2장의 "오래 사는 프로세스").

여기서 두 가지 실무 문제가 나옵니다.

### 1. 옛 프론트엔드 + 새 백엔드

배포 직후, 어제 코드를 들고 있는 브라우저가 오늘 배포한 API를 호출합니다. **API를 바꿀 때 하위 호환을 지켜야 하는 이유** 가 백엔드끼리의 문제가 아니라 여기에도 있습니다.

> 필드를 지우거나 이름을 바꾸는 변경은 **프론트엔드가 충분히 교체된 뒤에** 하세요.

### 2. 청크를 못 찾는 에러

코드 스플리팅(22장)을 쓰면 화면을 이동할 때 추가 파일을 받아옵니다. 그런데 그 사이 배포가 일어나 **파일 이름이 바뀌면**, 옛 페이지가 없어진 파일을 요청하게 됩니다.

```
ChunkLoadError: Loading chunk 42 failed
```

프론트엔드에서 아주 흔한 에러입니다. 대응은 두 가지입니다.

- **옛 파일을 얼마간 남겨둡니다.** 대부분의 호스팅이 알아서 해줍니다
- **이 에러를 잡아서 새로고침을 안내합니다.** "새 버전이 배포되었습니다. 새로고침해 주세요."

### 캐싱 전략

```
index.html          →  쓰기 전에 매번 확인   (진입점이 갱신되어야 하니까)
main.a3f9c2.js      →  오래 재사용해도 됨    (내용이 바뀌면 이름이 바뀌니까)
```

파일 이름에 내용 해시가 들어갑니다. **내용이 바뀌면 이름이 바뀌므로**, 이름이 같으면 내용도 같다고 믿을 수 있습니다. 그래서 마음 놓고 오래 캐시합니다. 자세한 것은 26장에서.

## 흔한 오해

**"Prettier와 ESLint는 같은 일을 한다"**
Prettier는 모양만, ESLint는 의미를 봅니다. 둘 다 씁니다.

**"빌드가 CI에서 통과했으니 타입도 검사됐다"**
프레임워크에 따라 다릅니다. `next build`는 검사하고, 변환기만 쓰는 구성은 안 합니다. 확인하고, 어느 쪽이든 앞쪽에 `tsc --noEmit`을 두세요.

**"프론트엔드는 테스트하기 어려우니 E2E만 두자"**
E2E는 느리고 잘 깨집니다. 컴포넌트 테스트가 중심이어야 합니다.

**"커버리지 100%를 목표로 하자"**
구현 세부를 테스트하는 쪽으로 밀려납니다. **깨졌을 때 사용자에게 문제가 생기는 것** 을 테스트하세요.

**"배포하면 모든 사용자가 새 버전을 쓴다"**
새로고침할 때까지 옛 코드입니다.

## 핵심 3가지

- **정적 검사는 셋을 구분합니다.** Prettier(모양), ESLint(의미), TypeScript(타입). 타입 검사는 빌드에 포함되기도 하지만, 앞쪽에 따로 두면 훨씬 빨리 실패합니다.
- **테스트의 중심은 컴포넌트 테스트입니다.** 역할과 이름으로 요소를 찾고, 구현 세부가 아니라 사용자가 보는 것을 검증합니다. 시맨틱 마크업이 여기서 보상받습니다.
- **배포해도 사용자는 옛 코드를 들고 있습니다.** API 하위 호환과 청크 로드 실패 대응이 필요합니다.
