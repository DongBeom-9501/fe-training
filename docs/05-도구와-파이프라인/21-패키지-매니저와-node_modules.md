# 21. 패키지 매니저와 node_modules

> **이 장의 질문**: `npm install` 한 번에 왜 파일이 수만 개 생기고, 그중 무엇을 믿어야 하는가?

10장에서 `package.json`을 읽는 법을 봤습니다. 이 장은 그 다음 — **설치를 누르면 실제로 무슨 일이 벌어지는가** 입니다.

## BE로 치면 이런 것

Gradle이 의존성을 해결하는 과정을 떠올려 보세요. 당신이 선언한 라이브러리가 또 다른 라이브러리를 끌고 오고, 그게 또 끌고 옵니다. 같은 라이브러리의 다른 버전이 둘 이상 나타나면 Gradle은 **하나를 골라 통일합니다.** 이걸 의존성 조정(conflict resolution)이라고 하죠.

JavaScript 생태계는 이 문제를 **정반대로** 풉니다.

> **하나로 통일하지 않습니다. 여러 버전을 동시에 설치합니다.**

이 한 문장이 `node_modules`의 모든 기이함을 설명합니다.

## 문제 상황

당신의 프로젝트가 두 라이브러리를 씁니다.

```
my-app
├── chart-lib   → lodash@3 이 필요
└── form-lib    → lodash@4 가 필요
```

JVM이라면 골치 아픈 상황입니다. 클래스패스에는 `lodash`가 하나만 올라갈 수 있으니, 하나를 고르고 나머지는 "잘 되기를" 빌어야 합니다. 안 되면 셰이딩(shading)으로 패키지 이름을 바꿔 넣습니다.

Node는 그냥 둘 다 설치합니다.

```
node_modules/
├── chart-lib/
│   └── node_modules/
│       └── lodash/        ← v3
├── form-lib/
│   └── node_modules/
│       └── lodash/        ← v4
```

**각 모듈이 자기 `node_modules`를 가질 수 있고, 찾을 때는 위로 거슬러 올라갑니다.** `chart-lib` 안에서 `require('lodash')`를 하면 자기 옆의 v3을 찾고, `form-lib`은 자기 옆의 v4를 찾습니다. 충돌이 원천적으로 없습니다.

대가는 **디스크와 파일 개수** 입니다. 중간 규모 프로젝트의 `node_modules`가 수만 개 파일에 수백 MB인 이유입니다.

## 평탄화 — 그리고 유령 의존성

버전이 겹치지 않는 대부분의 경우, 중첩은 낭비입니다. 그래서 npm과 yarn은 **가능한 것을 최상단으로 끌어올립니다.**

```
node_modules/
├── lodash/       ← 겹치지 않으면 여기 하나만
├── chart-lib/
└── form-lib/
```

여기서 실무에 영향을 주는 부작용이 하나 생깁니다.

```json
// package.json — 나는 lodash를 선언한 적이 없다
{ "dependencies": { "chart-lib": "^2.0.0" } }
```
```js
import _ from 'lodash';   // ✅ 그런데 동작한다
```

`chart-lib`이 끌고 온 `lodash`가 최상단에 올라와 있어서, **선언하지도 않은 패키지를 쓸 수 있게 됩니다.** 이걸 **유령 의존성(phantom dependency)** 이라고 합니다.

동작하니까 넘어가기 쉬운데, 언젠가 터집니다. `chart-lib`이 업데이트되면서 `lodash`를 떼어내거나 버전을 올리는 순간, **내가 건드리지도 않은 코드가 깨집니다.** 원인을 찾기가 대단히 어렵습니다.

Gradle로 치면 `implementation` 대신 전이 의존성에 무임승차하는 것과 같습니다. 백엔드에서도 하면 안 되는 일이죠.

> **예방**: 쓰는 것은 전부 `package.json`에 직접 선언하세요. 아래에서 볼 pnpm은 이걸 구조적으로 막습니다.

## npm / yarn / pnpm

셋 다 같은 저장소(npm 레지스트리)를 씁니다. 다른 것은 **어떻게 배치하느냐** 입니다.

| | 배치 방식 | 특징 |
| --- | --- | --- |
| **npm** | 평탄화 | Node에 기본 포함. 무난함 |
| **yarn** | 평탄화 | npm보다 먼저 락 파일을 도입했던 도구 |
| **pnpm** | **전역 저장소 + 링크** | 빠르고 디스크를 아낌. 유령 의존성 차단 |

**pnpm이 어떻게 다른가.** 패키지 실물을 컴퓨터 한 곳에 딱 한 번만 저장하고, 각 프로젝트의 `node_modules`에는 그리로 가는 링크만 둡니다.

```
~/.pnpm-store/            ← 실물은 여기 한 벌
프로젝트A/node_modules/    ← 링크
프로젝트B/node_modules/    ← 링크 (같은 실물을 가리킴)
```

프로젝트 10개가 같은 React를 써도 디스크에는 한 벌입니다. 그리고 **`package.json`에 선언한 것만 최상단에 링크하기 때문에** 유령 의존성이 아예 만들어지지 않습니다.

> **선택**: 새로 시작한다면 pnpm을 권합니다. 이미 npm으로 돌아가는 프로젝트라면 굳이 바꾸지 않아도 됩니다. **중요한 건 팀에서 하나만 쓰는 것** 입니다. 두 도구가 섞이면 락 파일이 둘이 되고, 사람마다 다른 것이 설치됩니다.

## 설치 명령을 구분해서 쓰기

| 명령 | 하는 일 | 언제 |
| --- | --- | --- |
| `npm install` | 락 파일을 **갱신할 수 있음** | 새 패키지를 추가할 때 |
| `npm ci` | 락 파일 **그대로** 설치. `node_modules`를 지우고 새로 | **CI에서는 반드시 이것** |
| `npm update` | 허용 범위 안에서 최신으로 올림 | 의도적으로 업데이트할 때 |

`ci`는 "continuous integration"의 약자입니다. **CI에서 `npm install`을 쓰면 락 파일이 바뀔 수 있어서, 내 노트북에서 되던 것이 CI에서 안 되는 상황이 생깁니다.** pnpm은 `pnpm install --frozen-lockfile`이 같은 역할입니다.

## 워크스페이스 — 모노레포

한 저장소 안에 여러 패키지를 두는 구조입니다. Gradle 멀티 모듈 프로젝트와 같은 자리입니다.

```
repo/
├── package.json          ← 워크스페이스 선언
├── apps/
│   ├── admin/
│   └── landing/
└── packages/
    └── ui/               ← admin과 landing이 함께 씀
```

```json
{ "workspaces": ["apps/*", "packages/*"] }
```

이러면 `packages/ui`를 `npm publish` 없이 `apps/admin`에서 `import` 할 수 있습니다. 의존성 설치도 한 번에 됩니다.

**필요할 때만 쓰세요.** 앱이 하나뿐이라면 모노레포는 순수한 복잡도 증가입니다.

## 의존성을 고르는 기준

프론트엔드 생태계는 패키지가 많고 진입장벽이 낮습니다. 그만큼 **버려진 패키지도 많습니다.** 넣기 전에 확인할 것들입니다.

| 확인 | 왜 |
| --- | --- |
| 마지막 릴리스가 언제인가 | 2년 넘게 조용하면 의심 |
| 이슈에 답이 달리는가 | 유지보수자가 살아 있는가 |
| 주간 다운로드 수 | 문제가 생겼을 때 검색이 되는가 |
| 번들 크기 | 사용자에게 전송됩니다 (22장) |
| 의존성 개수 | 하나 넣으면 몇 개가 딸려오는가 |
| 타입 정의 포함 여부 | `@types/` 를 따로 깔아야 하는가 |

**백엔드보다 신중해야 하는 이유가 하나 더 있습니다.** 서버 라이브러리는 무거워도 서버에만 있지만, **프론트엔드 라이브러리는 사용자의 회선으로 전송됩니다.** 날짜 포맷 하나 때문에 300KB를 내려받게 하는 일이 실제로 벌어집니다.

## 취약점 관리

```bash
npm audit              # 알려진 취약점 조회
npm audit fix          # 호환 범위 안에서 자동 수정
```

백엔드에서 하던 것과 같습니다. 다만 두 가지가 다릅니다.

**1. 노이즈가 많습니다.** `node_modules`가 크니 경고도 많이 나오고, 그중 상당수는 빌드 도구에만 있어서 **사용자에게 전송되지 않는** 패키지입니다. 심각도만 보고 놀라지 말고 **어디에 쓰이는 의존성인지** 를 보세요.

**2. 자동화가 필요합니다.** 사람이 주기적으로 돌리면 반드시 밀립니다. Dependabot이나 Renovate 같은 봇이 PR을 열어주게 해두는 것이 표준입니다. 자세한 것은 23장에서.

## 흔한 오해

**"node_modules가 크면 앱도 무겁다"**
아닙니다. `node_modules`는 개발 기계에만 있습니다. 사용자에게 가는 것은 빌드 결과물이고, 거기에는 **실제로 `import` 한 것만** 들어갑니다(22장).

**"패키지 매니저는 아무거나 써도 된다"**
프로젝트마다 하나여야 합니다. 락 파일이 둘이 되는 순간 재현성이 깨집니다.

**"의존성은 최신으로 유지하는 게 좋다"**
보안 패치는 빨리, 메이저 업그레이드는 신중히. 프론트엔드 메이저 업그레이드는 빌드 도구 체인 전체를 건드리는 경우가 많습니다.

**"`npm audit`에 경고가 하나도 없어야 한다"**
현실적으로 어렵습니다. **사용자에게 전송되는 코드의 취약점** 을 우선 처리하세요.

## 핵심 3가지

- **Node는 버전 충돌을 통일로 풀지 않습니다.** 여러 버전을 동시에 설치하고 각자 자기 것을 찾게 합니다. `node_modules`가 거대한 이유입니다.
- **평탄화가 유령 의존성을 만듭니다.** 선언하지 않은 패키지가 우연히 동작하다가, 남의 업데이트에 터집니다. 쓰는 것은 전부 직접 선언하세요.
- **CI에서는 `npm ci`** 를 씁니다. `npm install`은 락 파일을 바꿀 수 있어서 재현성이 깨집니다.
