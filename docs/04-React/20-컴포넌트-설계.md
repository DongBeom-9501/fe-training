# 20. 컴포넌트 설계 — 분리 기준과 합성

> **이 장의 질문**: 컴포넌트를 언제, 어떤 기준으로 쪼개야 하는가?

## BE로 치면 이런 것

클래스를 언제 나눌지 당신은 이미 감이 있습니다. 단일 책임, 응집도, 결합도. **그 감각은 여기서도 거의 그대로 통합니다.**

다만 프론트엔드에는 백엔드에 없는 기준이 하나 더 있습니다. **상태를 어디에 둘 것인가** 입니다. 컴포넌트를 나누면 코드가 정리되는 동시에 상태를 더 좁은 자리에 넣을 수 있게 되고, 그러면 그 상태가 바뀔 때 영향을 받는 범위가 줄어듭니다.

## 나쁜 기준 세 가지

먼저 흔히 쓰이지만 잘 안 되는 기준부터 걷어냅시다.

### ❌ "재사용할 것 같으니까"

가장 흔한 함정입니다. 아직 한 번밖에 안 쓰는데 미리 일반화하면, 실제로 두 번째 사용처가 생겼을 때 요구사항이 달라서 결국 props가 늘어나고 조건 분기가 붙습니다.

> **두 번째 사용처가 실제로 생겼을 때 뽑아내세요.** 백엔드에서 성급한 추상화를 피하는 것과 같습니다.

### ❌ "파일이 길어서"

200줄이 넘으면 나눠야 한다는 규칙은 없습니다. **하나의 응집된 관심사라면 300줄이어도 괜찮고, 두 가지 일을 하고 있다면 50줄이어도 나눠야 합니다.**

다만 길이는 **신호** 입니다. 길어지고 있다면 "여기서 몇 가지 일을 하고 있지?"를 물어볼 때입니다.

### ❌ "화면의 시각적 구획대로"

디자인 시안의 박스마다 컴포넌트를 만들면, 데이터 흐름과 무관한 경계가 생겨서 props가 여러 단계로 흘러내려갑니다.

## 좋은 기준 네 가지

### ✅ 1. 하나의 관심사인가

컴포넌트를 한 문장으로 설명해 보세요. **"그리고"가 들어가면 나눌 후보입니다.**

```
"주문 목록을 보여준다"                    → 좋음
"주문 목록을 보여주고 필터도 관리한다"      → 나눌 후보
```

### ✅ 2. 상태의 소유권이 다른가

**이게 프론트엔드 고유의 기준이고, 가장 강력합니다.**

어떤 상태가 화면의 일부에서만 쓰인다면, 그 일부를 컴포넌트로 뽑아서 상태를 그 안에 넣으세요.

```tsx
// ❌ 모달의 열림 상태가 페이지 전체를 리렌더시킨다
function OrderPage() {
  const [orders, setOrders] = useState([]);
  const [isModalOpen, setIsModalOpen] = useState(false);   // 여기 있을 필요가 없다
  return (
    <>
      <HugeTable orders={orders} />     {/* 모달 열 때마다 같이 리렌더 */}
      <button onClick={() => setIsModalOpen(true)}>추가</button>
      {isModalOpen && <Modal onClose={() => setIsModalOpen(false)} />}
    </>
  );
}

// ✅ 모달 상태를 자기 자리로 내린다
function OrderPage() {
  const [orders, setOrders] = useState([]);
  return (
    <>
      <HugeTable orders={orders} />
      <AddOrderButton />
    </>
  );
}

// 모달 상태가 이 안으로 들어왔다. 여기서 setState 해도 시작 지점이 여기다.
function AddOrderButton() {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <>
      <button onClick={() => setIsOpen(true)}>추가</button>
      {isOpen && <Modal onClose={() => setIsOpen(false)} />}
    </>
  );
}
```

17장에서 "상태 끌어올리기"를 배웠는데, **그 반대도 똑같이 중요합니다. 필요 없이 위에 있는 상태는 내리세요.**

### ✅ 3. 자주 바뀌는 상태를 가둘 수 있는가

18장에서 봤듯 `setState`는 그 컴포넌트에서 시작해 아래로 렌더를 다시 시도합니다. **시작 지점을 아래로 내리면 그만큼 범위가 줄어듭니다.**

한 가지 주의. 컴포넌트를 나눈다고 자식 렌더가 저절로 막히지는 않습니다. 부모가 다시 렌더되면 자식도 따라 내려갑니다. 여기서 얻는 것은 **"어디서부터 시작하느냐"** 이지 "어디서 멈추느냐"가 아닙니다. 멈추는 것은 `memo` 같은 별도 도구의 일입니다(35장).

```tsx
// 입력 중에 타이핑할 때마다 페이지 전체가 리렌더되는 것을 막는다
function SearchSection({ onSearch }: { onSearch: (q: string) => void }) {
  const [text, setText] = useState('');   // 타이핑 상태를 여기 가둠
  return <input value={text} onChange={e => setText(e.target.value)} onBlur={() => onSearch(text)} />;
}
```

> 다만 **측정 없이 성능을 위해 나누지는 마세요.** 대부분의 리렌더는 싸고, 구조가 자연스러우면 성능도 대개 따라옵니다.

### ✅ 4. 데이터를 가져오는가, 보여주기만 하는가

```
컨테이너(데이터를 가져오고 상태를 관리)  ←→  프레젠테이션(props만 받아서 그림)
```

**프레젠테이션 컴포넌트는 테스트하기 쉽고, 재사용되고, 스토리북 같은 도구에 올리기 좋습니다.** 서버에서 데이터를 어떻게 가져오든 무관하기 때문입니다.

> 나중에 배울 **서버 컴포넌트 / 클라이언트 컴포넌트** 경계(24장)와 헷갈리기 쉬운데 같은 것이 아닙니다. 그쪽은 "브라우저 API가 필요한가, 상호작용이 있는가"로 갈리는 실행 위치의 경계입니다. 다만 이 습관을 들여두면 그때 경계를 긋기가 수월합니다.

## prop drilling과 그 해법

컴포넌트를 잘게 나누다 보면 이런 상황이 생깁니다.

```tsx
// user가 3단계를 그냥 통과만 한다
<Page user={user}>
  <Layout user={user}>
    <Sidebar user={user}>
      <Profile user={user} />   {/* 여기서만 실제로 쓴다 */}
```

중간 컴포넌트들은 `user`를 쓰지도 않으면서 받아서 넘깁니다. 이걸 **prop drilling** 이라고 합니다.

해법이 세 가지 있는데, **순서가 중요합니다.**

### 해법 1: 합성 — `children`으로 뚫기 (가장 먼저 시도)

```tsx
// 부모가 완성된 것을 만들어서 통째로 내려보낸다
<Page>
  <Layout sidebar={<Sidebar><Profile user={user} /></Sidebar>}>
    ...
  </Layout>
</Page>
```

`Layout`과 `Sidebar`는 이제 `user`를 몰라도 됩니다. **JSX도 값이기 때문에(16장) props로 넘길 수 있다** 는 성질을 쓰는 것입니다.

**prop drilling의 대부분은 이걸로 해결됩니다.** 그런데 잘 안 알려져 있어서 다들 바로 Context로 갑니다.

### 해법 2: Context — 진짜 전역적인 것만

```tsx
const UserContext = createContext<User | null>(null);

// 위에서 제공 (React 19 문법. 이전에는 <UserContext.Provider value={user}>)
<UserContext value={user}>...</UserContext>

// 아래 어디서든 사용
const user = useContext(UserContext);
```

편하지만 대가가 있습니다.

- **값이 바뀌면 그 Context를 쓰는 모든 컴포넌트가 리렌더됩니다**
- 어디서 값이 오는지 추적하기 어려워집니다
- 컴포넌트가 그 Context 없이는 못 쓰이게 됩니다 (테스트가 번거로워짐)

> **적합한 것**: 로그인 사용자, 테마, 언어 설정처럼 **거의 안 바뀌고 정말 앱 전체가 쓰는 것.**
> **부적합한 것**: 자주 바뀌는 값, 화면 일부만 쓰는 값.

### 해법 3: 상태 관리 라이브러리 (28장)

Context로도 안 될 때 갑니다. 대부분은 여기까지 안 옵니다.

## 파일 구조

정답은 없지만, 실무에서 잘 버티는 형태는 이렇습니다.

```
src/
├── app/                    라우팅 (Next.js, 23장)
├── components/
│   ├── ui/                 도메인을 모르는 것 — Button, Input, Modal
│   └── orders/             도메인별 — OrderTable, OrderRow, OrderForm
├── hooks/                  공용 커스텀 훅
└── lib/                    API 클라이언트, 유틸
```

핵심은 **`ui/`와 도메인 폴더를 구분하는 것** 입니다. `Button`은 주문을 몰라야 하고, `OrderTable`은 주문을 알아도 됩니다. 백엔드의 공통 모듈과 도메인 모듈 구분과 같습니다.

> **작게 시작하세요.** 파일 3개짜리 프로젝트에 이 구조를 미리 만들 필요는 없습니다. 같은 폴더에 쌓이다가 불편해질 때 나누면 됩니다.

## 이름 짓기


백엔드와 같은 기준입니다. **파일명과 컴포넌트명을 같게** 맞추면 검색이 쉬워집니다. (내보내기 방식은 10장에서 정한 대로 named export를 기본으로 씁니다. Next.js 페이지 파일처럼 프레임워크가 default export를 요구하는 자리만 예외입니다.)

## 흔한 오해

**"컴포넌트는 작을수록 좋다"**
너무 잘게 나누면 props를 따라다니느라 읽기가 더 어렵습니다. **한 화면을 이해하는 데 파일을 몇 개 열어야 하는가** 도 비용입니다.

**"Context를 쓰면 prop drilling이 해결된다"**
`children` 합성을 먼저 시도하세요. Context는 리렌더 비용과 추적 어려움을 함께 가져옵니다.

**"컴포넌트를 나누면 성능이 좋아진다"**
자동으로 좋아지진 않습니다. 상태가 그에 맞게 내려가야 의미가 있습니다.

**"디자인 시안의 박스가 곧 컴포넌트다"**
데이터 흐름과 상태 소유권이 더 중요한 기준입니다.

## 핵심 3가지

- **"재사용할 것 같아서"는 나쁜 기준입니다.** 두 번째 사용처가 실제로 생겼을 때 뽑아내세요.
- **좋은 기준은 상태의 소유권입니다.** 화면 일부에서만 쓰는 상태는 그 일부 안으로 내리세요. 상태 끌어올리기의 반대도 똑같이 중요합니다.
- **prop drilling은 `children`부터 시도하세요.** Context는 리렌더 비용과 추적 어려움을 함께 가져옵니다.
