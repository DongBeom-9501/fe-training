# 18. state와 렌더링 사이클 — 재조정과 key

> **이 장의 질문**: `setState`를 부르면 정확히 무슨 일이 일어나는가?

## BE로 치면 이런 것

당신이 엔티티 필드를 바꾸고 트랜잭션을 커밋하면, JPA가 더티 체킹을 해서 **바뀐 컬럼만** UPDATE 문을 만듭니다. 당신은 SQL을 쓰지 않았고, 무엇이 바뀌었는지 계산하지도 않았습니다.

React의 state가 정확히 그 자리입니다. 값을 바꾸면 React가 **화면의 어느 부분이 달라졌는지 계산해서 그 부분만 DOM에 반영합니다.**

## state — 컴포넌트가 기억하는 값

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  //     ↑현재값  ↑변경함수         ↑초기값

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

props(17장)와의 차이는 하나입니다.

| | props | state |
| --- | --- | --- |
| 누가 소유 | 부모 | 자기 자신 |
| 바꿀 수 있나 | ❌ 읽기 전용 | ✅ setter로만 |
| 바뀌면 | 부모가 다시 렌더할 때 갱신 | **리렌더가 일어남** |

## 왜 그냥 변수를 쓰면 안 되나

```tsx
// ❌ 이건 동작하지 않는다
function Counter() {
  let count = 0;
  return <button onClick={() => { count++; }}>{count}</button>;
}
```

두 가지가 잘못됐습니다.

1. **컴포넌트 함수는 렌더될 때마다 처음부터 다시 실행됩니다.** `let count = 0`이 매번 다시 실행되므로 값이 살아남지 못합니다
2. **`count++`는 React에게 아무것도 알리지 않습니다.** 리렌더가 일어나지 않으니 화면이 그대로입니다

`useState`는 이 두 가지를 해결합니다. **값을 React가 보관해 두고, setter가 호출되면 리렌더를 예약합니다.**

> 컴포넌트가 함수인데 값이 어떻게 살아남는지 — 이 질문의 답은 [심화 가이드 9~10장](../../react-guide/README.md)에 있습니다. 지금은 "React가 컴포넌트의 트리 위치별로 따로 보관한다"고만 알면 충분합니다.

## setState는 즉시 반영되지 않는다

가장 많이 놀라는 지점입니다.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(count + 1);
    console.log(count);        // 0 — 방금 1로 바꿨는데?
  };
}
```

**`setCount`는 변수에 대입하는 것이 아니라 "다음 렌더는 이 값으로 해줘"라고 예약하는 것** 입니다. 지금 실행 중인 이 함수 안의 `count`는 **이번 렌더의 값** 이고, 끝까지 바뀌지 않습니다.

React는 각 렌더를 **그 시점 state의 스냅샷** 으로 다룹니다. 사진 한 장이라고 생각하면 됩니다. 나중에 값이 바뀌어도 이미 찍힌 사진은 그대로입니다.

이 성질 때문에 이런 일이 벌어집니다.

```tsx
const handleClick = () => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
};
// count는 3이 아니라 1이 된다
```

세 줄 모두 `count`가 0인 사진을 보고 있으니 전부 `setCount(0 + 1)`입니다.

**해결책은 "최신 값을 기준으로 계산해줘"라고 함수를 넘기는 것입니다.**

```tsx
setCount(c => c + 1);   // 세 번 호출하면 실제로 3이 된다
```

> **실무 규칙**: **이전 값을 기준으로 계산하는 업데이트는 항상 함수형으로 쓰세요.** `setCount(count + 1)` 대신 `setCount(c => c + 1)`. 습관을 들이면 이 부류의 버그를 통째로 피할 수 있습니다.

## 배칭 — 리렌더는 몰아서 한 번

한 이벤트 안에서 `setState`를 여러 번 불러도 **리렌더는 한 번만** 일어납니다.

```tsx
const handleSubmit = () => {
  setLoading(true);
  setError(null);
  setPage(1);
  // 리렌더는 세 번이 아니라 한 번
};
```

React가 이벤트 핸들러가 끝날 때까지 기다렸다가 몰아서 처리합니다. **배칭(batching)** 이라고 부릅니다. 화면이 중간 상태로 깜빡이는 것을 막고, 렌더 횟수를 줄여 줍니다.

## state는 불변으로 다뤄야 한다

React는 **참조 비교** 로 변경을 판단합니다(7장). 같은 객체를 내용만 바꿔서 넘기면 **React는 안 바뀐 줄 압니다.**

```tsx
// ❌ 화면이 갱신되지 않는다
const handleAdd = () => {
  orders.push(newOrder);     // 같은 배열
  setOrders(orders);         // 참조가 같으니 React는 무시
};

// ✅ 새 배열을 만든다
const handleAdd = () => {
  setOrders([...orders, newOrder]);
};
```

8장의 전개 구문이 여기서 매일 쓰입니다.

```tsx
setOrders([...orders, newOrder]);                                    // 추가
setOrders(orders.filter(o => o.id !== id));                          // 삭제
setOrders(orders.map(o => o.id === id ? { ...o, status: 'X' } : o));  // 수정
setForm({ ...form, email: 'a@b.c' });                                // 객체 필드 변경
```

## 리렌더 — 무엇이 다시 그려지나

`setState`가 호출되면 React는 **그 컴포넌트와 그 아래 전부** 를 다시 렌더합니다.

```
    App
     └── OrderPage        ← 여기서 setState
          ├── SearchBar   ← 다시 렌더됨
          └── OrderTable  ← 다시 렌더됨
               └── OrderRow ×100  ← 전부 다시 렌더됨
```

**"다시 렌더된다"는 "화면이 다시 그려진다"가 아닙니다.** 컴포넌트 함수가 다시 실행되어 새 JSX를 만들고, React가 그것을 이전 결과와 비교할 뿐입니다. 결과가 같으면 **DOM은 전혀 건드리지 않습니다.**

```
컴포넌트 함수 실행 (렌더)  →  이전 결과와 비교 (재조정)  →  다른 부분만 DOM 반영 (커밋)
     자주 일어남                  싸다                        비싸다. 최소한만
```

그래서 리렌더가 100번 일어나도 화면이 안 바뀌었으면 DOM 조작은 0번입니다. **리렌더 자체를 과하게 무서워할 필요는 없습니다.** 다만 렌더 함수 안에서 무거운 계산을 하고 있다면 그게 비용이 됩니다(35장).

## 재조정과 key

React가 이전 결과와 새 결과를 비교하는 과정을 **재조정(reconciliation)** 이라고 합니다. 규칙은 두 개뿐입니다.

**규칙 1: 타입이 다르면 통째로 버린다**

```tsx
{isEditing ? <input /> : <span />}
```

`input` → `span`으로 바뀌면 비교하지 않고 파괴 후 재생성합니다. 안에 있던 state도 사라집니다.

**규칙 2: 목록은 `key`로 동일성을 판단한다**

```tsx
{orders.map(o => <OrderRow key={o.id} order={o} />)}
```

`key`는 **"이 요소는 이전의 그 요소와 같은 것"** 이라고 알려주는 식별자입니다. 데이터베이스의 PK와 같은 역할입니다.

### 왜 인덱스를 key로 쓰면 안 되나

```tsx
{orders.map((o, i) => <OrderRow key={i} order={o} />)}   // ❌
```

목록 맨 앞에 항목이 하나 추가되면 이렇게 됩니다.

```
이전:  key=0 → ORD-1     새로:  key=0 → ORD-NEW
       key=1 → ORD-2            key=1 → ORD-1
                                key=2 → ORD-2
```

React는 "key=0인 요소의 내용이 ORD-1에서 ORD-NEW로 바뀌었다"고 판단합니다. **모든 행이 바뀐 것으로 취급되어 전부 다시 그려집니다.** 성능도 손해지만, 더 큰 문제는 **각 행이 가지고 있던 상태가 엉뚱한 행으로 옮겨간다** 는 것입니다.

체크박스를 켜둔 행이 있었다면, 그 체크 상태가 다른 주문에 붙습니다. 입력 중이던 값도 마찬가지입니다.

> **규칙**: `key`에는 **데이터의 고유 ID** 를 쓰세요. 목록이 절대 재정렬·추가·삭제되지 않는다고 확신할 때만 인덱스가 허용됩니다.

### key로 상태를 리셋하기

역으로 이 성질을 활용할 수도 있습니다.

```tsx
{/* 선택한 주문이 바뀌면 폼 내부 상태를 통째로 초기화 */}
<OrderForm key={selectedId} orderId={selectedId} />
```

`key`가 바뀌면 React는 다른 컴포넌트로 보고 새로 만듭니다. 안의 state도 초기화됩니다. **실무에서 아주 자주 쓰는 관용구** 입니다.

## 흔한 오해

**"setState는 즉시 반영된다"**
아닙니다. 다음 렌더에 반영됩니다. 이번 렌더의 값은 끝까지 그대로입니다.

**"리렌더 = 화면 다시 그리기"**
아닙니다. 함수 재실행이고, DOM 반영은 결과가 달라졌을 때만 일어납니다.

**"리렌더는 무조건 나쁘다"**
대부분 싸고 정상입니다. 문제가 되는 건 렌더 안의 무거운 계산과 너무 많은 DOM입니다.

**"state를 직접 바꾸고 setState로 같은 걸 넘기면 된다"**
참조가 같아서 React가 무시합니다. 새 객체·배열을 만들어야 합니다.

**"key는 React가 경고를 안 내게 하는 형식적인 것"**
diff 알고리즘의 입력값입니다. 잘못 넣으면 상태가 엉뚱한 행으로 옮겨갑니다.

## 핵심 3가지

- **`setState`는 예약입니다.** 즉시 바뀌지 않습니다. 이번 렌더의 값은 스냅샷처럼 고정되어 있습니다.
- **이전 값 기반 업데이트는 함수형으로.** `setCount(count + 1)` 대신 `setCount(c => c + 1)`. 습관을 들이면 이 부류의 버그가 사라집니다.
- **`key`는 형식이 아니라 diff의 입력값입니다.** 배열 인덱스를 쓰면 목록이 바뀔 때 상태가 엉뚱한 행으로 옮겨갑니다.

2. 체크박스가 있는 목록에서 `key={index}`를 쓰고 맨 앞에 항목을 추가하면 무슨 일이 벌어지는가?
