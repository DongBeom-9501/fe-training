# 16. 명령형에서 선언형으로 — `UI = f(state)`

> **이 장의 질문**: React는 무엇을 대신해 주는가?

## BE로 치면 이런 것

당신은 이미 선언형을 씁니다.

```sql
SELECT * FROM orders WHERE status = 'PAID'
```

이 한 줄에는 **"어떤 인덱스를 타고, 어떤 순서로 스캔하라"** 가 없습니다. **원하는 결과** 만 적었고, 도달 방법은 DB가 정합니다. 그래서 데이터가 늘어나도, 인덱스가 바뀌어도 이 쿼리는 그대로입니다.

React가 화면에 대해 하는 일이 정확히 같습니다.

```
명령형:  "스피너를 켜라. 에러를 숨겨라. 테이블을 지워라. 행을 12개 그려라."
선언형:  "로딩 중이면 스피너, 에러면 에러 화면, 아니면 테이블."
```

## 문제 상황

15장까지 배운 것으로 주문 목록 화면을 만들어 봅시다. 요구사항은 소박합니다.

- 목록을 보여준다
- 로딩 중엔 스피너
- 실패하면 에러
- 결과가 없으면 "주문이 없습니다"

```js
// ❌ 명령형 — 화면을 고치는 명령을 순서대로 나열한다
async function loadOrders() {
  spinner.style.display = 'block';
  errorBox.style.display = 'none';
  emptyBox.style.display = 'none';
  refreshBtn.disabled = true;

  try {
    const orders = await fetchOrders();
    tbody.replaceChildren();
    for (const o of orders) {
      const tr = document.createElement('tr');
      for (const value of [o.id, o.status]) {
        const td = document.createElement('td');
        td.textContent = value;      // textContent — 문자열을 HTML로 해석하지 않는다
        tr.appendChild(td);
      }
      tbody.appendChild(tr);
    }
    if (orders.length === 0) emptyBox.style.display = 'block';
  } catch (e) {
    errorBox.textContent = e.message;
    errorBox.style.display = 'block';
  } finally {
    spinner.style.display = 'none';
    refreshBtn.disabled = false;
  }
}
```

동작은 합니다. 문제는 **여기서부터** 입니다.

**"지금 로딩 중인가?"에 답하려면 어디를 봐야 할까요?** `spinner`의 `display` 속성입니다. 화면이 곧 데이터 저장소가 되어버렸습니다. 그리고 이 저장소에는 스키마도 제약조건도 없어서, **스피너는 보이는데 버튼은 활성화된** 조합이 얼마든지 만들어집니다. 한 줄만 빠뜨리면 됩니다.

요구사항이 하나 늘 때마다("로딩 중엔 필터도 비활성화") 고쳐야 할 곳이 여러 군데로 번집니다.

특히 **서로 독립적인 on/off 플래그** 가 늘어날 때가 문제입니다. 플래그가 3개면 표현 가능한 조합이 8가지인데, 그중 말이 되는 조합은 몇 개뿐입니다. 나머지는 전부 버그이고, 그걸 사람이 손으로 막고 있는 셈입니다.

## React의 답

**상태를 화면에서 빼내 한 곳에 모으고, 화면은 그 상태로부터 계산되게 합니다.**

아래 코드에 처음 보는 것이 두 개 나옵니다.

- **`useState`** — React가 제공하는 함수입니다. `[현재 값, 값을 바꾸는 함수]` 한 쌍을 돌려줍니다. 자세한 것은 18장에서 다룹니다.
- **`Result`** — 이 화면이 가질 수 있는 상태를 나열한 타입입니다. 입문 11장의 판별 유니온입니다.

```ts
type Result =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; orders: Order[] }
  | { status: 'error';   message: string };
```

```tsx
// ✅ 선언형 — 각 상태일 때 화면이 어떻게 생겼는지만 쓴다
function OrderList() {
  const [result, setResult] = useState<Result>({ status: 'idle' });

  async function load() {
    setResult({ status: 'loading' });
    try {
      const orders = await fetchOrders();
      setResult({ status: 'success', orders });
    } catch (e) {
      setResult({ status: 'error', message: (e as Error).message });
    }
  }

  if (result.status === 'loading') return <Spinner />;
  if (result.status === 'error')   return <ErrorBox message={result.message} />;
  if (result.status === 'success' && result.orders.length === 0) return <Empty />;
  return <Table orders={result.status === 'success' ? result.orders : []} onRefresh={load} />;
}
```

**`spinner.style.display`를 건드리는 코드가 한 줄도 없다는 점** 을 보세요. 화면을 고치는 일은 아무도 하지 않습니다. 상태만 바꾸면 화면이 따라옵니다.

한 줄로 쓰면 이렇습니다.

```
UI = f(state)
```

같은 상태에는 항상 같은 화면. 순수 함수입니다.

## 무엇이 좋아졌나

| | 명령형 | React |
| --- | --- | --- |
| 상태의 위치 | DOM 속성에 흩어짐 | `useState` 한 곳 |
| 불가능한 조합 | 얼마든지 생김 | **타입이 막아줌** (아래) |
| 요구사항 추가 | 여러 곳 수정 | 상태 정의 한 곳 |
| 무엇이 바뀌었나 | 개발자가 계산 | React가 계산 |
| 화면 갱신 | 다 지우고 다시 그림 | 바뀐 부분만 |

**두 번째 줄이 특히 큽니다.** 11장의 판별 유니온을 여기에 쓰면 이렇게 됩니다.

```ts
type Result =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; orders: Order[] }
  | { status: 'error';   message: string };
```

이 타입에서는 **"로딩 중인데 데이터가 있는"** 상태를 표현할 방법 자체가 없습니다. 불가능한 조합이 컴파일 단계에서 사라집니다. Kotlin의 sealed class로 상태 기계를 모델링하는 것과 같은 이야기입니다.

> 이게 React를 쓰는 백엔드 개발자의 강점이 나오는 지점입니다. **화면 상태를 도메인 모델처럼 설계하는 습관** 이 그대로 통합니다.

## JSX — HTML처럼 생긴 JavaScript

위 코드에 섞여 있던 HTML 비슷한 문법이 JSX입니다. 새로운 언어가 아니라 **함수 호출로 컴파일되는 문법 설탕** 입니다.

```tsx
<button className="btn" onClick={save}>저장</button>
```
```js
// 실제로는 이렇게 변환된다 (개념적으로)
createElement('button', { className: 'btn', onClick: save }, '저장')
```

그래서 JSX는 **값** 입니다. 변수에 담고, 배열에 넣고, 함수에서 반환할 수 있습니다.

```tsx
const rows = orders.map(o => <tr key={o.id}><td>{o.id}</td></tr>);
```

### 문법 규칙 다섯 개

```tsx
// 1. 중괄호 안은 JavaScript 표현식
<td>{order.amount.toLocaleString()}원</td>

// 2. class → className, for → htmlFor (예약어라서)
<label htmlFor="email" className="text-sm">이메일</label>

// 3. 반환은 하나의 루트여야 한다. 감쌀 태그가 없으면 <>...</>
return (
  <>
    <Header />
    <Table />
  </>
);

// 4. 조건부는 && 또는 삼항 연산자 (if 문은 표현식이 아니라 못 씀)
{isAdmin && <DeleteButton />}
{isLoading ? <Spinner /> : <Table />}

// 5. 목록은 map, 각 요소에 key
{orders.map(o => <OrderRow key={o.id} order={o} />)}
```

**4번의 함정**: `&&`의 왼쪽이 숫자 `0`이면 화면에 `0`이 그대로 찍힙니다(7장의 falsy 이야기).

```tsx
{orders.length && <Table />}        {/* ❌ 0건이면 화면에 "0"이 나온다 */}
{orders.length > 0 && <Table />}    {/* ✅ */}
```

## 컴포넌트 — 화면의 함수

컴포넌트는 **JSX를 반환하는 함수** 입니다. 그게 전부입니다.

```tsx
function OrderRow({ order }: { order: Order }) {
  return (
    <tr>
      <td>{order.id}</td>
      <td>{order.status}</td>
    </tr>
  );
}
```

규칙은 두 개뿐입니다.

1. **이름이 대문자로 시작해야 합니다.** 소문자면 React가 HTML 태그로 취급합니다
2. **JSX를 반환합니다** (또는 `null`)

## 선언형의 대가

공짜는 아닙니다. 포기하는 것이 있습니다.

**1. 세밀한 제어를 잃습니다.** "이 셀만 정확히 바꿔라"를 지시할 수 없습니다. SQL에서 실행 계획을 직접 못 짜는 것과 같습니다. 대개 이득이지만, 성능이 문제될 때는 우회 수단이 필요합니다(25장).

**2. 오버헤드가 있습니다.** React는 항상 일을 더 합니다. 그 대가로 예측 가능성을 삽니다. [React 심화 가이드 4장](../../react-guide/docs/01-React의-계약/04-가상-DOM의-진실.md)에서 이 거래를 정면으로 다룹니다.

**3. 명령형이 필요한 순간은 여전히 있습니다.** 포커스 이동, 스크롤 위치, 외부 라이브러리 연결. 그때는 `useRef`로 내려갑니다(19장). **나쁜 게 아니라 경계에서만 쓰는 것** 입니다.

## 흔한 오해

**"React는 DOM 조작을 쉽게 해주는 라이브러리다"**
반대에 가깝습니다. React는 DOM을 직접 만지지 **않아도 되게** 만드는 라이브러리입니다. 마음먹으면 만질 수는 있습니다. 다만 그러면 같은 DOM을 관리하는 주인이 둘이 되어 예측이 무너집니다. 그 절제가 이득의 원천입니다.

**"React를 쓰면 빨라진다"**
빨라지는 게 아니라 **예측 가능해집니다.** 성능은 오히려 손해 보는 경우도 있습니다.

**"JSX는 HTML이다"**
JavaScript입니다. `class`가 `className`인 이유가 그것입니다.

**"컴포넌트는 클래스 같은 것이다"**
함수입니다. 인스턴스가 없습니다. 이 차이가 18~19장에서 중요해집니다.

## 핵심 3가지

- **문제는 화면이 상태 저장소가 된 것입니다.** 그래서 불가능한 조합이 만들어지고, 요구사항 하나에 수정 지점이 번집니다.
- **React는 상태를 한 곳에 모읍니다.** 화면은 그 상태로부터 계산됩니다. `UI = f(state)`.
- **JSX는 HTML이 아닙니다.** 함수 호출로 컴파일되는 JavaScript 표현식이고, 컴포넌트는 JSX를 반환하는 함수일 뿐입니다.
