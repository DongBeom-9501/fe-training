# 3. 주소창에 URL을 넣으면 벌어지는 일

> **이 장의 질문**: 엔터를 치고 화면이 뜨기까지, 내가 아는 부분은 어디까지고 모르는 부분은 어디부터인가?

## BE로 치면 이런 것

이 질문은 당신이 면접에서 이미 답해봤을 겁니다. DNS 조회하고, TCP 연결하고, TLS 핸드셰이크하고, HTTP 요청 보내고, 로드밸런서 거쳐서, 서버가 응답하고 — 여기까지는 당신의 홈그라운드입니다.

그런데 대부분의 백엔드 개발자는 **"서버가 200 OK와 HTML을 반환했다"에서 이야기를 끝냅니다.** 프론트엔드 개발자에게는 바로 거기서 이야기가 **시작** 합니다.

이 장은 그 뒷부분입니다.

## 당신이 아는 절반 (빠르게)

```
1. URL 파싱          https://admin.example.com/orders?page=2
                     프로토콜 / 호스트 / 경로 / 쿼리
2. DNS 조회          admin.example.com → 93.184.216.34
3. TCP 연결          3-way handshake
4. TLS 핸드셰이크     인증서 검증, 세션 키 교환
5. HTTP 요청 전송     GET /orders?page=2
6. (서버가 일한다)
7. 응답 수신          200 OK + HTML 본문
```

여기까지 걸리는 시간은 보통 수십~수백 밀리초입니다. 그리고 **이때까지 화면은 아직 하얗습니다.**

## 모르는 절반: 응답을 받은 다음

브라우저는 HTML을 통째로 다 받고 나서 일을 시작하지 않습니다. **바이트가 도착하는 대로 위에서부터 읽어 내려가면서** 처리합니다. 그러다 이런 것을 만납니다.

```html
<link rel="stylesheet" href="/style.css">
<script src="/app.js"></script>
<img src="/logo.png">
```

이 줄들은 각각 **새로운 HTTP 요청** 입니다. 브라우저는 HTML을 읽다가 이걸 발견하는 즉시 또 요청을 보냅니다. 그리고 그 파일 안에서 또 다른 파일을 참조하면 또 요청을 보냅니다.

```
HTML 요청 ─────┐
               ├─ CSS 요청 ────┐
               │               └─ 폰트 요청
               ├─ JS 요청 ─────┐
               │               └─ 추가 JS 청크 요청
               └─ 이미지 요청 ×12
```

**핵심**: 사용자가 페이지 하나를 여는 것은 요청 한 번이 아니라 **요청 수십 번** 입니다. 실제 서비스에서 50~100개는 흔합니다.

이것이 백엔드 성능 감각과 크게 어긋나는 첫 지점입니다. 서버 응답이 50ms로 빨라도, 그 뒤에 딸려오는 요청들이 순차적으로 줄줄이 이어지면 사용자가 보는 화면은 3초 뒤에 뜹니다. 이 줄줄이 사탕을 **워터폴(waterfall)** 이라고 부르고, 개발자 도구의 Network 탭이 정확히 이걸 보여줍니다.

> 워터폴을 짧게 만드는 기술들 — 번들링, 코드 스플리팅, preload — 은 22장과 26장에서 다룹니다. (요즘 브라우저와 서버는 한 연결에서 여러 요청을 겹쳐 처리하므로, 요청 개수 자체보다 **서로 기다려야 하는 단계가 몇 겹인지** 가 더 중요합니다.) 지금은 "요청이 여러 개고, 그게 성능을 결정한다"만 가져가면 됩니다.

## 렌더링을 막는 것들

모든 요청이 똑같이 중요하진 않습니다. 그중 두 가지는 **화면 그리기를 멈춰 세웁니다.**

막는 방식이 두 가지라서 나눠 봐야 합니다.

- **파서 차단** — HTML을 계속 읽어 내려가는 것 자체를 멈춥니다
- **렌더 차단** — 파싱은 계속되지만 화면을 그리지 않고 기다립니다

| 리소스 | HTML 파싱 | 첫 렌더 | 왜 |
| --- | --- | --- | --- |
| CSS | 계속됨 | **막는다** | 스타일을 모르면 잘못된 모습으로 그렸다가 다시 그려야 합니다 |
| `<script>` (기본) | **막는다** | 막는다 | JS가 HTML을 바꿀 수 있어서, 실행이 끝나야 다음을 읽습니다 |
| `<script defer>` | 안 막는다 | 안 막는다 | 다운로드는 병렬로, 실행은 HTML 파싱이 끝난 뒤 |
| `<script async>` | **막을 수 있다** | 간접적으로 | 다운로드가 끝나는 순간 실행되는데, 그 시점이 파싱 도중이면 멈춥니다 |
| 이미지 | 안 막는다 | 안 막는다 | 나중에 채워 넣으면 됩니다 |

`async`가 특히 헷갈립니다. **"기다리지 않는다"이지 "멈추지 않는다"가 아닙니다.** CSS처럼 "이게 올 때까지 화면을 안 그리겠다"는 게 아니라, **다운로드가 끝나는 순간 끼어들어 실행되면서 그동안 다른 일을 못 하게 하는** 쪽입니다. 언제 끼어들지 모르니 실행 시점도 순서도 예측할 수 없습니다. 그래서 실무에서는 대개 `defer`를 씁니다.

그래서 "CSS는 `<head>`에, JS는 `</body>` 직전에" 라는 오래된 관습이 생겼습니다. 요즘은 `defer`를 쓰거나 프레임워크가 알아서 처리하지만, **왜 그랬는지** 는 알아 두는 게 좋습니다. 화면이 하얗게 멈춰 있는 원인을 찾을 때 여기가 첫 번째 용의자입니다.

## Origin — 앞으로 계속 나올 개념

브라우저는 **오리진(origin)** 단위로 보안 경계를 긋습니다. 오리진은 이 셋의 조합입니다.

```
프로토콜 + 호스트 + 포트
https   ://  admin.example.com  :443
```

| URL | `https://admin.example.com` 과 같은 오리진인가 |
| --- | --- |
| `https://admin.example.com/orders` | ✅ 같다 (경로는 무관) |
| `http://admin.example.com` | ❌ 프로토콜이 다름 |
| `https://api.example.com` | ❌ 호스트가 다름 |
| `https://admin.example.com:8443` | ❌ 포트가 다름 |

**브라우저는 기본적으로 다른 오리진의 응답을 JavaScript가 읽지 못하게 막습니다.** 이게 동일 출처 정책(Same-Origin Policy)이고, 당신이 겪게 될 CORS 에러의 뿌리입니다.

여기서 백엔드 개발자가 가장 많이 오해하는 지점을 미리 짚어 둡니다.

> **CORS는 "이 응답을 JS에게 넘겨줘도 되는가"를 브라우저가 판정하는 정책입니다.** 서버가 요청을 거부한 것과는 다른 층위의 문제라서, Postman에서는 되고 브라우저에서만 안 되는 상황이 생깁니다.

다만 "서버는 항상 200을 응답했다"고 단정하면 틀립니다. 두 경우가 있습니다.

| 경우 | 무슨 일이 | Network 탭에서 |
| --- | --- | --- |
| 단순 요청 | 요청은 서버에 도달했고 응답도 왔지만, 브라우저가 JS에게 안 넘겨줌 | 요청 1개, 상태 코드는 정상 |
| **사전 요청(preflight)** | 브라우저가 본 요청 전에 `OPTIONS`를 먼저 보내고, 여기서 막히면 **본 요청은 아예 안 나감** | `OPTIONS` 요청이 실패로 찍힘 |

> **디버깅 규칙**: Network 탭에서 `OPTIONS` 요청이 있는지부터 보세요. 그게 실패했다면 서버는 진짜 요청을 받아본 적조차 없습니다.

자세한 것은 37장에서 다룹니다.

## 화면이 뜬 다음에도 끝이 아니다

HTML이 다 그려지면 백엔드의 세계관에서는 "응답 완료"입니다. 프론트엔드에서는 이제 시작입니다.

```
   HTML 도착 → 화면 그림 → JS 실행 → 이벤트 붙임 → 사용자 조작 → 화면 갱신 → 사용자 조작 → …
   └──────────── 1초 ────────────┘  └──────────── 세 시간 ────────────────────┘
```

2장에서 말한 "오래 사는 프로세스"가 시작되는 지점이 바로 여기입니다. 그 이후로는 페이지를 다시 로드하지 않고, JS가 화면을 직접 고쳐 씁니다. 어떻게 고쳐 쓰는지가 5장, 왜 한 번에 하나씩만 할 수 있는지가 6장입니다.

## 흔한 오해

**"서버 응답이 빠르면 페이지도 빠르다"**
서버 응답은 전체의 일부입니다. 응답 후에 딸려오는 수십 개의 요청과 JS 실행 시간이 훨씬 큰 경우가 많습니다. 24장에서 이걸 지표로 재는 법을 다룹니다.

**"CORS는 서버 설정 문제다"**
설정으로 푸는 건 맞지만, **누가 막았는지** 를 이해해야 디버깅이 됩니다. 막은 건 브라우저입니다.

**"HTML을 다 받아야 화면이 그려진다"**
아닙니다. 브라우저는 스트리밍으로 처리합니다. 이 성질을 적극적으로 쓰는 것이 32장의 스트리밍 SSR입니다.

## 핵심 3가지

- **200 OK는 끝이 아니라 시작입니다.** DNS·TCP·TLS·HTTP까지는 당신이 아는 대로입니다. 그 뒤가 프론트엔드의 영역입니다.
- **요청은 한 번이 아니라 수십 번입니다.** 브라우저가 HTML을 읽으면서 CSS·JS·이미지를 줄줄이 더 요청합니다. 그중 CSS는 첫 렌더를, 기본 `<script>`는 파싱까지 막습니다.
- **오리진이 경계입니다.** 프로토콜·호스트·포트가 하나라도 다르면 다른 오리진이고, 여기서 CORS가 나옵니다.
