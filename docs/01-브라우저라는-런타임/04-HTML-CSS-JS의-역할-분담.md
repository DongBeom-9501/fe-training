# 4. HTML / CSS / JS의 역할 분담

> **이 장의 질문**: 왜 화면 하나를 만드는 데 언어가 세 개나 필요한가?

## BE로 치면 이런 것

백엔드에서도 우리는 한 덩어리로 안 짭니다. 엔티티, 서비스, 컨트롤러를 나누죠. 이유는 각각이 바뀌는 이유가 다르기 때문입니다. 스키마가 바뀌는 것과 비즈니스 규칙이 바뀌는 것과 API 스펙이 바뀌는 것은 서로 다른 사건입니다.

웹 화면도 똑같은 이유로 셋으로 나뉩니다.

| 파일 | 담당 | 바뀌는 이유 |
| --- | --- | --- |
| **HTML** | 구조와 의미 — 여기 무엇이 있는가 | 담을 내용이 바뀔 때 |
| **CSS** | 표현 — 어떻게 보이는가 | 디자인이 바뀔 때 |
| **JavaScript** | 행동 — 무엇에 반응하는가 | 기능이 바뀔 때 |

"주문 목록"이라는 사실(HTML)과 "테이블은 줄무늬 배경"이라는 결정(CSS)과 "행을 클릭하면 상세가 열린다"는 규칙(JS)은 서로 독립적으로 바뀝니다. 그래서 파일이 분리되어 있습니다.

## 문제 상황

셋을 안 나누면 이런 코드가 됩니다. 실제로 2000년대 웹은 이랬습니다.

```html
<!-- 나쁜 예: 세 관심사가 한 줄에 뒤엉켜 있다 -->
<div style="color:red; font-weight:bold" onclick="document.getElementById('x').style.display='block'">
  주문 상세 보기
</div>
```

문제가 보이시나요.

- 디자이너가 색을 바꾸려면 HTML을 고쳐야 합니다
- 같은 스타일을 100군데 쓰면 100군데를 고쳐야 합니다
- `div`라서 키보드로 접근할 수 없고, 스크린 리더는 이게 버튼인지 모릅니다
- 로직이 마크업 속에 문자열로 박혀 있어서 테스트할 수 없습니다

## 세 언어의 성격

세 언어는 성격이 아주 다릅니다. 이걸 알고 가야 각 파트가 왜 그렇게 생겼는지 이해됩니다.

| | HTML | CSS | JavaScript |
| --- | --- | --- | --- |
| 종류 | 마크업 언어 | 선언형 규칙 집합 | 범용 프로그래밍 언어 |
| 로직 | 없음 | 거의 없음 | 전부 |
| 에러가 나면 | 브라우저가 알아서 고침 | 그 줄만 무시 | **거기서 멈춤** |
| 대응되는 것 | DTO / 스키마 | 설정 파일 | 서비스 로직 |

**에러 처리 방식의 차이가 특히 중요합니다.** HTML과 CSS는 관대합니다. 태그를 안 닫아도 브라우저가 추측해서 고치고, 모르는 CSS 속성은 그냥 건너뜁니다. 반면 JS는 에러가 나면 그 지점에서 실행이 멈춥니다.

이 비대칭에서 실무 규칙 하나가 나옵니다.

> **중요한 것일수록 아래쪽 계층에 두어라.**
> JS가 깨져도 HTML만으로 읽을 수 있는 화면이 안전한 화면입니다.

## 세 계층이 각각 실패하면

| 무엇이 실패하면 | 사용자가 보는 것 |
| --- | --- |
| 이미지 로드 실패 | 나머지는 멀쩡, 이미지 자리만 빔 |
| CSS 로드 실패 | 못생겼지만 **내용은 다 읽힘** |
| JS 로드/실행 실패 | 화면은 떠 있는데 **아무것도 안 눌림** |
| HTML 응답 실패 | 아무것도 없음 |

세 번째가 가장 고약합니다. 사용자 눈에는 정상으로 보이는데 반응이 없거든요. 29장에서 다룰 "하이드레이션 실패"가 정확히 이 증상입니다.

## 코드 읽기

같은 화면을 셋으로 나눠 쓰면 이렇게 됩니다.

**HTML — 무엇이 있는가**
```html
<button class="btn-primary" id="refresh">새로고침</button>
<table class="order-table">
  <tr><td>ORD-1001</td><td>결제완료</td></tr>
</table>
```

**CSS — 어떻게 보이는가**
```css
.btn-primary { background: #2563eb; color: white; padding: 8px 16px; }
.order-table tr:nth-child(even) { background: #f8fafc; }
```

**JavaScript — 무엇에 반응하는가**
```js
// 새로고침 버튼을 누르면 목록을 다시 불러온다
document.getElementById('refresh').addEventListener('click', () => {
  loadOrders();
});
```

Kotlin/Java 개발자에게 가장 낯선 건 아마 CSS일 겁니다. **CSS에는 호출이 없습니다.** `.btn-primary`라고 쓰면 "이 클래스를 가진 모든 요소에 이 규칙이 적용된다"는 선언일 뿐, 누가 언제 호출하는지가 없습니다. 그래서 전역 설정 파일에 가깝고, 13장에서 다룰 "충돌"이라는 고유한 문제가 생깁니다.

## React를 쓰면 이 분리는 어떻게 되나

미리 말해 둡니다. 4부에서 배울 React는 **이 세 가지를 한 파일에 다시 모읍니다.**

```jsx
// 구조 + 행동이 한 곳에
<button className="bg-blue-600 text-white px-4 py-2" onClick={loadOrders}>
  새로고침
</button>
```

배신처럼 보이지만 아닙니다. 분리의 기준이 **파일 종류**에서 **컴포넌트**로 바뀐 것입니다. "모든 버튼의 스타일을 한 파일에" 대신 "이 버튼에 관한 모든 것을 한 곳에"로요.

백엔드에서 레이어드 아키텍처(controller/service/repository 패키지로 나누기)에서 패키지 바이 피처(주문 관련은 order 패키지에 다 모으기)로 옮겨가는 흐름과 정확히 같은 이야기입니다. **기술 종류로 나눌 것인가, 기능 단위로 나눌 것인가.** 프론트엔드는 후자로 옮겨갔습니다.

다만 **역할 자체는 여전히 셋** 입니다. 한 파일에 있어도 구조·표현·행동은 구분해서 생각해야 합니다.

## 흔한 오해

**"HTML은 그냥 껍데기라 아무 태그나 써도 된다"**
`div`만 써도 화면은 똑같이 보입니다. 하지만 키보드 사용자, 스크린 리더, 검색엔진, 브라우저의 자동완성은 전부 태그의 의미를 읽습니다. 12장에서 다룹니다.

**"CSS는 디자이너 영역이라 몰라도 된다"**
레이아웃이 깨지는 버그는 대부분 개발자에게 옵니다. 13~14장만큼은 건너뛰지 마세요.

**"JS만 잘하면 된다"**
JS로 다 할 수는 있습니다. 하지만 HTML/CSS로 할 수 있는 일을 JS로 하면 느리고 깨지기 쉽습니다.

## 핵심 3가지

- **역할이 셋입니다.** HTML은 구조, CSS는 표현, JS는 행동. 각각 바뀌는 이유가 다르기 때문에 나뉘어 있습니다.
- **에러 처리가 비대칭입니다.** HTML과 CSS는 관대하고 JS는 멈춥니다. 그래서 중요한 것일수록 아래 계층에 두는 게 안전합니다.
- **React는 셋을 한 파일에 모읍니다.** 분리를 포기한 게 아니라, 분리 기준을 파일 종류에서 컴포넌트로 옮긴 것입니다.
