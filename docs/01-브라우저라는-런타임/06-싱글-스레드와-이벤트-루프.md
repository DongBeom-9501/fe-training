# 6. 싱글 스레드와 이벤트 루프

> **이 장의 질문**: JavaScript는 스레드가 하나뿐인데, 어떻게 여러 일을 동시에 하는 것처럼 보이는가?

이 장은 Part 1에서 가장 중요합니다. 백엔드 개발자의 동시성 직관이 여기서 한 번 크게 어긋나고, 9장(비동기)과 35장(성능)이 전부 이 위에 올라갑니다.

## BE로 치면 이런 것

당신의 서버는 요청이 100개 들어오면 스레드 100개(또는 코루틴 100개)가 동시에 처리합니다. 하나가 DB를 기다리며 블로킹되어도 나머지 99개는 잘 돕니다. 스레드풀 크기를 늘리면 처리량이 늘어납니다.

**브라우저에서 화면을 다루는 스레드는 하나뿐입니다.** 이걸 메인 스레드라고 부릅니다.

풀도 없고, 늘릴 수도 없습니다. 그 하나가 당신의 코드도 실행하고, 클릭도 처리하고, 화면도 그립니다. 하나가 막히면 **전부 막힙니다.**

> 정확히 말하면 브라우저에 JS 실행 환경이 하나뿐인 것은 아닙니다. Web Worker라는 별도 스레드가 있습니다(이 장 끝에서 다룹니다). 다만 **DOM을 만질 수 있는 것은 메인 스레드뿐** 이고, 화면과 관련된 일은 전부 거기서 벌어집니다. 그래서 실무 감각으로는 "하나"라고 생각하면 됩니다.

## 왜 하나뿐인가

DOM 때문입니다.

DOM은 거대한 공유 가변 상태입니다. 두 스레드가 동시에 같은 노드를 지우고 수정한다면 락이 필요하고, 데드락이 생기고, 개발자는 매번 동기화를 신경 써야 합니다. 웹 개발을 그렇게 만들 수는 없었습니다.

그래서 웹 플랫폼은 **"DOM을 만지는 스레드는 하나, 대신 아무도 락을 걱정하지 않는다"** 를 택했습니다. 이 선택 덕분에 프론트엔드 코드에는 `synchronized`도, `volatile`도, 경쟁 조건도 (거의) 없습니다.

**대가는 하나뿐입니다. 절대로 오래 붙잡고 있으면 안 됩니다.**

## 문제 상황

```js
// 이 코드가 실행되는 동안 페이지는 완전히 죽는다
function calculate() {
  let sum = 0;
  for (let i = 0; i < 5_000_000_000; i++) sum += i;
  return sum;
}
```

이 함수가 도는 3초 동안 사용자는 이런 상태입니다.

- 버튼을 눌러도 반응 없음
- 스크롤 안 됨
- 애니메이션 정지
- 텍스트 선택 안 됨
- 심지어 탭도 못 닫음

서버에서 무거운 계산을 하면 그 요청 하나만 느립니다. 브라우저에서 무거운 계산을 하면 **그 사용자의 화면 전체가 얼어붙습니다.** 이 차이가 결정적입니다.

## 구조: 콜 스택, 큐, 이벤트 루프

```
      ┌─────────────┐
      │  콜 스택     │  ← 지금 실행 중인 것 (하나뿐)
      └──────┬──────┘
             │ 비면 가져온다
      ┌──────┴──────────────────────┐
      │  ① 마이크로태스크 큐          │  Promise 콜백
      │  ② 태스크 큐                 │  클릭, 타이머, 네트워크 응답
      └─────────────────────────────┘
                   ↑
        브라우저의 다른 부분(별도 스레드)이 여기에 넣어준다
```

**이벤트 루프** 는 대략 이런 무한 반복입니다. (실제 명세는 더 복잡합니다. 아래는 실무에 필요한 만큼만 줄인 학습용 모델입니다.)

1. 콜 스택이 비었나?
2. 비었으면 마이크로태스크 큐를 **전부** 비운다
3. 그 다음 태스크 큐에서 **하나만** 꺼내 실행한다
4. **필요하고 여유가 있으면** 화면을 다시 그린다 — 매번 그린다는 보장은 없습니다
5. 1로 돌아간다

여기서 중요한 사실이 하나 있습니다. **네트워크 요청과 타이머는 JS 스레드가 처리하지 않습니다.** 브라우저 내부의 다른 (진짜) 스레드가 처리하고, 끝나면 결과를 큐에 넣어줍니다. JS 스레드는 그걸 꺼내 쓸 뿐입니다.

그래서 이런 일이 가능합니다.

```js
// 이 코드는 3초를 기다리지 않는다
fetch('/api/orders').then(res => console.log('도착'));  // 브라우저가 대신 기다림
console.log('먼저 찍힘');                                 // 즉시 실행
```

> 이것이 "싱글 스레드인데 어떻게 동시에?"의 답입니다. **JS는 기다리지 않습니다.** 기다림은 브라우저에게 위임하고, 자기는 다음 일을 합니다.

## Kotlin/Java와 대조

```kotlin
// Kotlin — 스레드를 실제로 재운다
Thread.sleep(1000)
println("1초 뒤")
// 이 스레드는 멈췄지만 다른 스레드들은 계속 돈다
```

```js
// JavaScript — 스레드를 재우는 게 아니라 "나중에 실행할 일"로 등록한다
setTimeout(() => console.log("1초 뒤"), 1000);
console.log("먼저 찍힘");   // ← 이게 먼저 나온다
```

```kotlin
// 코루틴이 가장 가깝다
suspend fun load() {
  val orders = api.getOrders()   // 스레드를 놓아준다
  println(orders)
}
```
```js
// async/await은 코루틴과 거의 같은 모양
async function load() {
  const orders = await api.getOrders();  // 이벤트 루프에 제어권을 돌려준다
  console.log(orders);
}
```

**모양은 코루틴과 거의 같습니다. 결정적인 차이는 돌아올 스레드가 하나뿐이라는 것입니다.** 코루틴은 다른 스레드에서 재개될 수 있지만, JS는 무조건 그 하나의 스레드로 돌아옵니다. 그래서 CPU를 오래 쓰는 작업은 `async`를 붙여도 소용이 없습니다.

> `await`은 스레드를 막지 않습니다. 하지만 `await` 사이에 있는 **동기 코드** 는 막습니다. 9장에서 자세히 다룹니다.

## 마이크로태스크가 먼저인 이유

큐가 두 개인 게 이상해 보일 수 있는데, 우선순위가 다릅니다.

```js
console.log('1');
setTimeout(() => console.log('2'), 0);      // 태스크 큐
Promise.resolve().then(() => console.log('3')); // 마이크로태스크 큐
console.log('4');

// 출력: 1 → 4 → 3 → 2
```

`setTimeout(fn, 0)`이 즉시 실행되지 않는 게 핵심입니다. **0ms는 "지금"이 아니라 "가능한 한 빨리, 단 지금 하던 일이 다 끝나고, 마이크로태스크도 다 끝난 뒤"** 라는 뜻입니다.

이 순서를 외울 필요는 없습니다. 다만 **"타이머는 최소 지연이지 정확한 시각이 아니다"** 는 기억해 두세요. 무거운 코드가 돌고 있으면 `setTimeout(fn, 100)`은 500ms 뒤에 실행될 수도 있습니다.

## 그래서 실무에서 지키는 것

| 하지 말 것 | 이유 | 대신 |
| --- | --- | --- |
| 반복문으로 수백만 건 계산 | 화면이 언다 | 서버에서 계산해서 내려주기 |
| 큰 배열 정렬/필터를 매 렌더마다 | 프레임 예산 초과 | 메모이제이션 (35장) |
| 거대한 JSON을 한 번에 파싱 | 파싱도 동기 작업 | 페이지네이션 |
| 수천 개 행을 한 번에 렌더 | 레이아웃 폭발 | 가상 스크롤 |

정말 무거운 계산이 필요하면 **Web Worker** 라는 별도 스레드를 쓸 수 있습니다. 다만 Worker는 DOM을 만질 수 없고 메시지로만 통신합니다 — 액터 모델과 같은 구조입니다. 실무에서 쓸 일은 드물어서 이 문서에서는 이름만 알려 드립니다.

## 흔한 오해

**"async를 붙이면 병렬로 실행된다"**
아닙니다. `async`는 병렬이 아니라 **양보** 입니다. CPU를 쓰는 작업은 `async`를 붙여도 여전히 화면을 멈춥니다.

**"`setTimeout(fn, 0)`은 즉시 실행된다"**
현재 실행 중인 모든 동기 코드와 마이크로태스크가 끝난 뒤에 실행됩니다.

**"싱글 스레드라서 느리다"**
대부분의 화면 작업은 CPU 바운드가 아니라 네트워크 대기입니다. 그리고 그 대기는 JS 스레드를 쓰지 않습니다. 실제 병목은 대개 "한 번에 너무 많이 그리려는 것"입니다.

**"경쟁 조건은 없다"**
락이 필요한 종류의 경쟁 조건은 없습니다. 하지만 "느린 응답이 빠른 응답보다 늦게 도착해서 옛 데이터가 화면을 덮어쓰는" 종류의 문제는 있습니다. 27장에서 다룹니다.

## 핵심 3가지

- **화면을 다루는 스레드는 하나뿐입니다.** DOM을 락 없이 다루기 위한 선택입니다. 대가로, 코드가 오래 실행되면 화면 전체가 얼어붙습니다.
- **JS는 기다리지 않습니다.** 네트워크와 타이머는 브라우저의 다른 부분이 처리하고 결과만 큐에 넣어줍니다. 이벤트 루프가 그걸 꺼내 씁니다.
- **`async/await`은 코루틴과 모양만 같습니다.** 돌아올 스레드가 하나뿐이라, CPU를 오래 쓰는 작업에는 도움이 되지 않습니다.
