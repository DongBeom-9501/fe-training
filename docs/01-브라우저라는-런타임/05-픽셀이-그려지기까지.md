# 5. 픽셀이 그려지기까지 — DOM, CSSOM, 레이아웃, 페인트

> **이 장의 질문**: 브라우저는 텍스트 파일을 받아서 어떻게 화면의 픽셀로 바꾸는가?

## BE로 치면 이런 것

당신이 SQL 한 줄을 던지면 DB는 이런 단계를 밟습니다.

```
SQL 텍스트 → 파싱 → 쿼리 트리 → 실행 계획 수립 → 실행 → 결과
```

그리고 당신이 느린 쿼리를 튜닝할 때는 `EXPLAIN`으로 **어느 단계에서 비용이 터지는지** 를 봅니다. 단계를 모르면 튜닝을 할 수 없습니다.

브라우저의 렌더링도 똑같습니다. 파이프라인이 있고, 각 단계에 비용이 있고, 성능 문제는 항상 "어느 단계가 몇 번 도는가"의 문제입니다.

## 렌더링 파이프라인

```
HTML ──파싱──> DOM  ┐
                    ├──> 렌더 트리 ──> 레이아웃 ──> 페인트 ──> 합성 ──> 화면
CSS  ──파싱──> CSSOM ┘
```

한 단계씩 봅니다.

### 1. DOM — HTML을 객체 트리로

브라우저는 HTML 텍스트를 파싱해서 **DOM(Document Object Model)** 이라는 트리를 만듭니다.

```html
<body>
  <h1>주문 목록</h1>
  <ul><li>ORD-1001</li></ul>
</body>
```
```
body
├── h1 ("주문 목록")
└── ul
    └── li ("ORD-1001")
```

DOM은 **파싱 결과이자 살아 있는 API** 입니다. JS가 `document.querySelector('h1')`로 이 트리의 노드를 잡아서 바꿀 수 있고, 바꾸면 화면이 따라 바뀝니다. 백엔드로 치면 XML을 파싱해서 만든 객체 트리인데, 그 객체를 수정하면 실시간으로 출력이 바뀌는 것과 같습니다.

> 4부에서 배울 React는 이 DOM을 **직접 만지지 않기 위해** 존재합니다. 이유는 16장에서.

### 2. CSSOM — CSS를 규칙 트리로

CSS도 같은 방식으로 파싱되어 **CSSOM** 이 됩니다. 여기서 "이 요소의 최종 스타일은 무엇인가"가 계산됩니다. 상속과 우선순위를 따져야 해서 생각보다 복잡한 계산이고, 13장에서 규칙을 다룹니다.

### 3. 렌더 트리 — 둘을 합치기

DOM과 CSSOM을 합쳐서 **실제로 화면에 그려질 것들만** 골라낸 트리를 만듭니다. `display: none`인 요소는 여기서 빠집니다.

> 여담이지만 `display: none`(렌더 트리에서 제외)과 `visibility: hidden`(자리는 차지하되 안 보임)의 차이가 여기서 나옵니다.

### 4. 레이아웃 — 위치와 크기 계산

각 요소가 **어디에, 얼마나 크게** 놓일지를 계산합니다. "너비 50%"는 부모가 정해져야 알 수 있고, 부모는 또 그 부모가 정해져야 알 수 있습니다. 그래서 이 단계는 트리 전체에 영향을 주며, **대체로 가장 비쌉니다.**

다른 이름으로 **리플로우(reflow)** 라고도 부릅니다.

### 5. 페인트 — 픽셀 채우기

색, 배경, 그림자, 텍스트를 실제 픽셀로 칠합니다. 레이아웃보다는 싸지만 여전히 비용이 있습니다. **리페인트(repaint)** 라고도 합니다.

### 6. 합성 — 레이어 겹치기

칠해진 결과를 여러 레이어로 나눠 GPU에서 합칩니다. 가장 쌉니다.

## 왜 이걸 알아야 하는가

**화면이 바뀔 때마다 이 파이프라인이 다시 돕니다.** 그런데 무엇이 바뀌었느냐에 따라 **어느 단계부터** 다시 도는지가 달라집니다.

| 무엇을 바꿨나 | 다시 도는 단계 | 대체로 |
| --- | --- | --- |
| `width`, `height`, `top`, `font-size`, 요소 추가/삭제 | 레이아웃 → 페인트 → 합성 | 🔴 비쌈 |
| `color`, `background`, `box-shadow` | 페인트 → 합성 | 🟡 중간 |
| `transform`, `opacity` | 합성만 (조건이 맞을 때) | 🟢 쌈 |

**"대체로"라고 쓴 이유가 있습니다.** `transform`과 `opacity`가 합성만 유발하려면 그 요소가 별도 레이어로 분리되어 있어야 하고, 레이어를 만드는 것 자체도 메모리 비용입니다. 레이어가 너무 많거나 크면 합성이 오히려 병목이 됩니다. 그래서 실무에서는 **추측하지 말고 개발자 도구의 Performance 탭에서 실제로 어느 단계가 도는지 확인** 합니다.

여기서 프론트엔드의 가장 유명한 성능 규칙이 나옵니다.

> **애니메이션은 `transform`과 `opacity`로 하라.**

요소를 오른쪽으로 100px 옮길 때 `left: 100px`로 하면 매 프레임 레이아웃이 다시 돌고, `transform: translateX(100px)`로 하면 합성만 다시 돕니다. 같은 결과인데 비용이 몇 배 차이 납니다.

백엔드로 치면 인덱스를 타는 쿼리와 풀스캔의 차이 같은 것입니다. 결과는 같지만 실행 계획이 다릅니다.

## 레이아웃 스래싱 — 대표적인 함정

이 코드는 느립니다.

```js
// 나쁜 예: 읽기와 쓰기를 번갈아 한다
for (const el of elements) {
  el.style.width = el.offsetWidth + 10 + 'px';
  //               ↑ 읽기(레이아웃 강제)   ↑ 쓰기(레이아웃 무효화)
}
```

브라우저는 원래 변경을 모아뒀다가 한 번에 처리합니다. 그런데 `offsetWidth` 같은 **계산된 값을 읽는 순간** "지금 당장 정확한 값이 필요하다"는 뜻이므로 레이아웃을 강제로 돌립니다. 그 다음 줄에서 다시 쓰면 무효화되고, 다음 반복에서 또 강제로 돌립니다. 요소가 100개면 레이아웃이 100번 돕니다.

**레이아웃 스래싱(layout thrashing)** 이라고 부릅니다. N+1 쿼리와 발생 원리가 똑같습니다 — 배치로 처리될 수 있는 일을 반복문 안에서 하나씩 강제 실행시키는 것.

```js
// 좋은 예: 읽기를 먼저 다 하고, 쓰기를 나중에 다 한다
const widths = elements.map(el => el.offsetWidth);   // 읽기 몰아서
elements.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px';            // 쓰기 몰아서
});
```

> 실무에서는 React가 이런 배치를 대신 해주기 때문에 직접 쓸 일은 드뭅니다. 다만 **왜 React가 그런 구조인지** 를 이해하려면 이 문제를 알아야 합니다.

## 16.7밀리초라는 예산

화면이 부드럽게 보이려면 초당 60프레임이 필요하고, 이는 **한 프레임당 16.7ms** 라는 뜻입니다. 이 안에 JS 실행 + 레이아웃 + 페인트 + 합성이 전부 끝나야 합니다.

백엔드에서 "이 API는 p99 200ms 이하" 같은 예산을 잡듯이, 프론트엔드에는 **프레임 예산** 이 있습니다. 이걸 넘기면 프레임이 밀리고, 사용자는 "버벅인다"고 느낍니다.

이 예산을 누가 어떻게 까먹는지는 다음 장의 주제입니다.

## 흔한 오해

**"DOM 조작이 느리다"**
정확히는 DOM 조작 자체가 아니라 그것이 유발하는 **레이아웃 재계산** 이 비쌉니다. 그래서 "DOM을 적게 만지자"보다 "레이아웃을 적게 유발하자"가 맞는 목표입니다.

**"CSS 애니메이션이 JS 애니메이션보다 무조건 빠르다"**
어느 속성을 바꾸느냐의 문제입니다. CSS로도 `width`를 애니메이션하면 느리고, JS로도 `transform`을 바꾸면 빠릅니다.

**"요소를 숨길 땐 `display: none`이 최고다"**
자주 토글되는 요소라면 렌더 트리에 넣었다 뺐다 하는 비용이 있습니다. 상황에 따라 `opacity` + `pointer-events`가 나을 수 있습니다.

## 핵심 3가지

- **파이프라인이 있습니다.** DOM과 CSSOM을 합쳐 렌더 트리를 만들고, 레이아웃 → 페인트 → 합성 순으로 그립니다.
- **어느 단계부터 다시 도는지가 비용입니다.** `transform`과 `opacity`는 대체로 합성만 다시 돌아 가장 쌉니다. 단, 실제로 그런지는 개발자 도구로 확인하세요.
- **읽기와 쓰기를 번갈아 하지 마세요.** 반복문 안에서 계산된 값을 읽고 스타일을 쓰면 레이아웃이 매번 강제 실행됩니다. N+1 쿼리와 같은 실수입니다.
