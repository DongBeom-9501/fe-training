# 12. HTML 시맨틱과 폼

> **이 장의 질문**: `div`로 다 만들어도 똑같이 보이는데, 왜 태그를 골라 써야 하는가?

## BE로 치면 이런 것

DTO 필드를 전부 `String`으로 선언한다고 생각해 보세요.

```kotlin
data class OrderDto(
  val a: String,   // 주문번호
  val b: String,   // 금액
  val c: String,   // 상태
)
```

동작은 합니다. 직렬화도 되고 API도 나갑니다. 그런데 이걸 받는 쪽은 아무것도 알 수 없습니다. 문서를 봐야 하고, 검증도 못 하고, IDE도 도와주지 못합니다.

**`div`만 쓰는 HTML이 정확히 이 상태입니다.** 화면은 똑같이 나오지만, 그 HTML을 읽는 다른 소비자들이 아무것도 알 수 없게 됩니다.

## HTML의 소비자는 사람만이 아니다

이게 핵심입니다. 당신의 HTML을 읽는 것은 눈으로 보는 사용자만이 아닙니다.

| 소비자 | 무엇을 읽나 | `div`만 쓰면 |
| --- | --- | --- |
| 브라우저 | 키보드 이동 순서, 기본 동작 | Tab으로 이동 불가, Enter로 실행 불가 |
| 스크린 리더 | 역할과 상태 | "그룹, 그룹, 그룹" — 아무 의미도 전달 안 됨 |
| 검색엔진 | 문서 구조와 중요도 | 무엇이 제목인지 모름 |
| 비밀번호 관리자 · 자동완성 | 입력 필드의 종류 | 채워주지 못함 |
| 브라우저 번역 · 리더 모드 | 본문 영역 | 오작동 |
| 테스트 코드 | 역할 기반 선택자 | 깨지기 쉬운 선택자를 써야 함 |

**시맨틱 태그는 "의미를 담은 타입"입니다.** `String` 대신 `OrderId`를 쓰는 것과 같은 이유로 씁니다.

## 문제 상황: div로 만든 버튼

```html
<!-- ❌ 보기에는 버튼 -->
<div class="btn" onclick="save()">저장</div>
```

이 "버튼"은 이런 것들이 안 됩니다.

- Tab 키로 이동할 수 없습니다 (포커스를 못 받음)
- Enter나 Space로 누를 수 없습니다
- 스크린 리더가 "버튼"이라고 읽어주지 않습니다
- `disabled` 속성이 동작하지 않습니다
- 폼 안에 넣어도 submit 되지 않습니다

이걸 `div`로 흉내 내려면 이렇게까지 해야 합니다.

```html
<div class="btn" role="button" tabindex="0"
     onclick="save()"
     onkeydown="if(event.key==='Enter'||event.key===' ') save()">저장</div>
```

```html
<!-- ✅ 그냥 이렇게 쓰면 전부 공짜 -->
<button onclick="save()">저장</button>
```

> **규칙**: 브라우저가 이미 해주는 일을 다시 구현하지 마세요. 백엔드에서 프레임워크가 해주는 트랜잭션 관리를 직접 짜지 않는 것과 같습니다.

## 알아둘 태그는 생각보다 적다

전부 외울 필요 없습니다. 실무에서 90%를 차지하는 것만.

### 문서 구조

```html
<header>   상단 영역 (로고, 전역 네비)
<nav>      네비게이션 링크 묶음
<main>     이 페이지의 주 콘텐츠 — 페이지당 하나
<section>  제목을 가지는 논리적 구획
<article>  그 자체로 독립적인 내용 (게시글, 카드)
<aside>    부가 정보 (사이드바)
<footer>   하단 영역
```

### 텍스트

```html
<h1>~<h6>  제목. 건너뛰지 말고 순서대로 (h1 다음에 h3 ❌)
<p>        문단
<ul>/<ol>/<li>  목록
<table>    진짜 표 데이터에만. 레이아웃 용도로 쓰지 않기
<strong>   중요함 (굵게가 아니라 "중요")
<em>       강조 (기울임이 아니라 "강조")
```

**제목 레벨은 글자 크기가 아니라 문서의 목차 구조** 입니다. 크기를 줄이고 싶으면 CSS로 하세요. 그리고 `<h1>`은 그 페이지가 무엇에 대한 것인지를 나타내므로, 관례적으로 하나만 둡니다(문법 규칙은 아닙니다).

### 상호작용

```html
<button>   무언가를 실행한다
<a href>   어딘가로 이동한다
```

**둘의 구분이 실무에서 계속 헷갈립니다. 기준은 하나입니다.**

| | 쓰는 경우 | 사용자가 기대하는 것 |
| --- | --- | --- |
| `<a href="...">` | **주소가 바뀐다** | 새 탭으로 열기, 링크 복사, 뒤로 가기 |
| `<button>` | 주소가 안 바뀐다 | 즉시 실행 |

목록에서 상세로 이동하는 것은 `<a>`입니다. 모달을 여는 것은 `<button>`입니다. `<a>`를 써야 할 곳에 `<button onClick={navigate}>`를 쓰면 사용자가 새 탭으로 열 수 없습니다 — 실무에서 아주 흔한 불만입니다.

## 폼 — 브라우저가 공짜로 주는 것

폼은 시맨틱의 이득이 가장 큰 영역입니다.

```html
<form onsubmit="handleSubmit(event)">
  <label for="email">이메일</label>
  <input id="email" name="email" type="email" required autocomplete="email" />

  <label for="amount">금액</label>
  <input id="amount" name="amount" type="number" min="0" step="100" />

  <button type="submit">저장</button>
</form>
```

이 마크업이 자동으로 주는 것들입니다.

- **`<label for>`** — 라벨을 클릭하면 입력창에 포커스가 갑니다. 스크린 리더가 "이메일, 편집 상자"라고 읽습니다
- **`type="email"`** — 모바일에서 `@`가 있는 키보드가 뜹니다
- **`type="number"`** — 숫자 키패드가 뜹니다
- **`required`** — 비어 있으면 브라우저가 막고 메시지를 띄웁니다
- **`autocomplete`** — 브라우저와 비밀번호 관리자가 값을 채워줍니다
- **`<form>` 안의 Enter 키** — 자동으로 submit 됩니다

마지막 항목이 특히 중요합니다. **`<form>` 없이 `<div>`에 input을 늘어놓으면 Enter로 제출이 안 됩니다.** 사용자는 이걸 버그로 인식합니다.

### type 목록

```
text  email  password  number  tel  url  search
date  time   datetime-local  file  checkbox  radio
```

`type`을 제대로 고르는 것만으로 모바일 사용성이 크게 달라집니다.

### 브라우저 검증은 UX일 뿐

`required`, `min`, `pattern` 같은 것들은 편의 기능입니다. **2장에서 말했듯 진짜 검증은 서버의 몫입니다.** 사용자는 개발자 도구로 속성을 지우고 보낼 수 있습니다.

## 접근성 — 최소한만

접근성은 넓은 주제입니다. 시맨틱 태그를 제대로 쓰는 것이 **가장 큰 한 걸음** 이지만 그것으로 끝은 아닙니다. 포커스가 눈에 보이는지, 색 대비가 충분한지, 에러 메시지가 입력창과 연결되어 있는지, 모달이 열렸을 때 포커스가 갇히는지는 따로 챙겨야 합니다.

여기서는 시맨틱 태그 다음으로 자주 필요한 것만 짚습니다.

```html
<!-- 이미지에는 대체 텍스트. 장식용이면 빈 문자열 -->
<img src="chart.png" alt="월별 주문 추이" />
<img src="divider.png" alt="" />

<!-- 아이콘만 있는 버튼에는 이름을 붙인다 -->
<button aria-label="닫기">✕</button>

<!-- 언어 선언 — 스크린 리더 발음과 번역에 영향 -->
<html lang="ko">
```

> **ARIA 제1 규칙**: `aria-*` 속성을 쓰지 않아도 되는 방법이 있다면 그걸 쓰세요. `<div role="button" tabindex="0">`보다 `<button>`이 항상 낫습니다.

## React에서는 어떻게 쓰나

거의 그대로입니다. 두 가지만 이름이 다릅니다. JSX의 속성은 HTML 속성 이름이 아니라 **DOM 프로퍼티 이름** 을 따르기 때문입니다.

```tsx
<label htmlFor="email">이메일</label>       {/* for → htmlFor */}
<div className="row">                       {/* class → className */}
```

브라우저의 DOM API에서도 이 둘은 `element.className`, `label.htmlFor`로 부릅니다. `class`와 `for`가 JavaScript 예약어라서 원래 그렇게 이름이 붙었고, JSX가 그 이름을 그대로 씁니다.

## 흔한 오해

**"시맨틱은 SEO 때문에 하는 것이다"**
SEO는 부수 효과입니다. 주된 이유는 키보드 접근성과 브라우저 기본 동작입니다.

**"우리 서비스는 사내 어드민이라 접근성은 필요 없다"**
스크린 리더 사용자만의 문제가 아닙니다. **키보드만으로 빠르게 입력하는 실무자** 가 가장 큰 수혜자입니다. 어드민이야말로 폼 접근성이 중요합니다.

**"`<div>`에 `role`을 붙이면 똑같다"**
키보드 동작은 따라오지 않습니다. 직접 구현해야 합니다.

**"`<strong>`은 굵게, `<em>`은 기울임"**
의미 태그입니다. 굵게만 원하면 CSS의 `font-weight`를 쓰세요.

## 핵심 3가지

- **HTML을 읽는 건 사람만이 아닙니다.** 브라우저, 스크린 리더, 검색엔진, 비밀번호 관리자, 테스트 코드가 전부 읽습니다.
- **`<a>`와 `<button>`은 주소가 바뀌는지로 고릅니다.** 이동이면 `<a>`, 실행이면 `<button>`입니다.
- **폼은 브라우저가 많은 걸 공짜로 줍니다.** `<form>`, `<label for>`, 알맞은 `type`만 쓰면 포커스 연결·모바일 키보드·자동완성·Enter 제출이 따라옵니다.
