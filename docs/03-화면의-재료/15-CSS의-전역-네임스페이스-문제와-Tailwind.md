# 15. CSS의 전역 네임스페이스 문제와 Tailwind

> **이 장의 질문**: CSS 문법은 다 아는데 왜 실무 CSS는 그렇게 잘 망가지는가?

## BE로 치면 이런 것

이런 코드베이스를 상상해 보세요.

- 모든 변수가 **전역** 입니다. `private`도 패키지도 없습니다
- 아무 파일에서나 다른 파일의 동작을 바꿀 수 있습니다
- 어떤 함수가 실제로 쓰이는지 **찾을 방법이 없습니다.** 지우면 어딘가 깨질 수도 있고 아닐 수도 있습니다
- 파일을 로드하는 순서가 동작을 바꿉니다

당신이라면 절대 이렇게 안 짜겠죠. **그런데 CSS는 구조적으로 그렇게 생겼습니다.**

```css
/* button.css */
.title { font-size: 20px; }
```
```css
/* card.css */
.title { font-size: 14px; }   /* 서로를 모른 채 충돌한다 */
```

이 둘은 서로의 존재를 모릅니다. 어느 쪽이 이길지는 **로드 순서** 가 정합니다(13장). 그리고 이 사실을 아무도 눈치채지 못한 채 몇 달이 지나갑니다.

## 여기서 파생되는 세 가지 고통

### 1. 이름 충돌

프로젝트가 커질수록 `.title`, `.item`, `.active` 같은 이름은 반드시 겹칩니다. 겹치면 **의도하지 않은 곳의 스타일이 바뀝니다.**

### 2. 지울 수 없는 CSS

```css
.legacy-order-badge { ... }   /* 이거 아직 쓰나? */
```

**알 방법이 없습니다.** 클래스 이름은 HTML 안에 문자열로 들어 있고, 심지어 JS가 동적으로 조합해서 만들 수도 있습니다. 정적 분석으로 찾을 수가 없습니다.

그래서 다들 지우지 않고 놔둡니다. CSS 파일은 **한 방향으로만 자랍니다.** 실무에서 CSS 번들이 수백 KB가 되는 이유입니다.

### 3. 고칠 때마다 무서워진다

`.btn`의 padding을 바꾸려는데, 이게 어디에 쓰이는지 모릅니다. 그래서 어떻게 할까요? **새 클래스를 만듭니다.**

```css
.btn { }
.btn-new { }
.btn-new-2 { }   /* 😱 */
```

이 세 가지가 합쳐지면, CSS는 **아무도 손대기 싫어하는 파일** 이 됩니다.

## 해결 시도의 역사

이 문제는 20년 넘게 프론트엔드 커뮤니티의 숙제였습니다. 해법이 순서대로 나왔고, **각각이 무엇을 포기하고 무엇을 얻었는지** 를 보면 지금의 선택이 이해됩니다.

### 1세대: BEM — 규율로 푼다

```css
.card { }
.card__title { }
.card__title--large { }
```

`블록__요소--수식어` 규칙으로 이름을 길게 만들어 충돌을 피합니다.

- ✅ 도구가 필요 없습니다
- ❌ **사람이 지켜야 합니다.** 한 명이 안 지키면 무너집니다
- ❌ 여전히 지울 수 없습니다

### 2세대: CSS Modules — 빌드가 이름을 바꿔준다

```css
/* Card.module.css */
.title { font-size: 20px; }
```
```tsx
import styles from './Card.module.css';
<h2 className={styles.title}>   {/* 실제로는 Card_title__x7f2a */}
```

빌드 시점에 이름에 해시를 붙여서 **충돌을 구조적으로 없앱니다.**

- ✅ 충돌이 사라집니다
- ✅ import를 따라가므로 어느 정도 추적 가능합니다
- ❌ 파일을 왔다 갔다 해야 합니다
- ❌ 여전히 안 쓰는 규칙이 파일에 남습니다

### 3세대: CSS-in-JS — JS로 스타일을 쓴다

```tsx
const Title = styled.h2`font-size: 20px;`;
```

- ✅ 컴포넌트와 스타일이 한 곳에, 타입 안전
- ❌ **런타임 방식** 은 렌더할 때마다 스타일을 계산해 주입하므로 비용이 있습니다
- ❌ 런타임 방식은 서버 컴포넌트(31장)와 손이 많이 갑니다

> 두 종류가 있습니다. **빌드 시점에 CSS 파일로 뽑아내는 방식** 도 있고, 이쪽은 위 단점이 없습니다. 최근 채택이 줄고 있는 것은 런타임 방식 쪽입니다.

### 4세대: Tailwind — 클래스를 만들지 않는다

발상을 뒤집습니다. **이름 충돌이 문제라면, 이름을 짓지 않으면 됩니다.**

```tsx
<h2 className="text-xl font-bold text-slate-900">주문 목록</h2>
```

각 클래스는 **미리 정의된 작은 유틸리티** 입니다. 대개 CSS 속성 하나에 대응하지만 항상 그런 건 아닙니다 — `text-xl`은 `font-size`와 함께 어울리는 `line-height`도 같이 잡아 줍니다.

## Tailwind가 세 고통을 어떻게 없애는가

| 고통 | Tailwind의 답 |
| --- | --- |
| 이름 충돌 | **새 이름을 짓지 않습니다.** 정해진 유틸리티만 조합하니 충돌할 대상이 없습니다 |
| 지울 수 없음 | 컴포넌트를 지우면 그 클래스도 같이 사라집니다. **CSS 파일이 한 방향으로 자라지 않습니다** |
| 고치기 무서움 | 이 클래스는 **이 요소에만** 영향을 줍니다. 다른 데를 깨뜨릴 수 없습니다 |

특히 두 번째가 큽니다. Tailwind는 빌드할 때 소스 코드를 훑어서 **실제로 등장한 클래스만 골라** CSS를 생성합니다. 그래서 프로젝트가 커져도 CSS 번들이 거의 안 자랍니다.

> **조건이 하나 있습니다.** 소스에서 **완전한 클래스 이름을 찾을 수 있어야** 합니다. 문자열로 조립하면 못 찾습니다. 이 장 끝에서 다시 짚습니다.

## 솔직한 단점

이 문서가 Tailwind를 택했다고 해서 단점을 숨기지는 않겠습니다.

**1. 마크업이 지저분해 보입니다.**

```tsx
<button className="inline-flex items-center gap-2 rounded-md bg-blue-600 px-4 py-2 text-sm font-medium text-white hover:bg-blue-700 disabled:opacity-50">
```

처음 보면 거부감이 듭니다. **정당한 반응입니다.** 다만 실무에서는 반복되는 것을 컴포넌트로 뽑아내기 때문에 이 문자열을 여러 번 쓰지 않습니다.

```tsx
// 한 번 만들고 계속 쓴다
<Button variant="primary">저장</Button>
```

핵심은 **"CSS 재사용 단위를 클래스에서 컴포넌트로 옮긴 것"** 입니다. 클래스를 재사용하지 않고 컴포넌트를 재사용합니다.

**2. 클래스 이름을 외워야 합니다.** 초반에 문서를 계속 봅니다. 다행히 규칙적이라 며칠이면 익숙해집니다.

**3. 관심사 분리를 어긴 것처럼 보입니다.** 입문 4장에서 이야기한 그 주제입니다 — **기술 종류로 나눌 것인가, 기능 단위로 나눌 것인가.** Tailwind는 후자를 택합니다.

## 왜 이 문서가 Tailwind를 택했나

백엔드 개발자에게 이 조합이 특히 잘 맞는다고 봅니다.

1. **CSS 설계를 배우지 않아도 됩니다.** 좋은 클래스 이름 짓기, 파일 구조 잡기는 그 자체로 난이도 있는 기술입니다. Tailwind는 그 단계를 건너뛰게 해줍니다
2. **디자인 시스템이 딸려 옵니다.** 간격은 4px 단위, 색은 정해진 팔레트. 임의의 값을 고민할 필요가 없습니다
3. **지역성이 높습니다.** 이 요소의 스타일이 이 줄에 다 있습니다. 다른 파일을 열 필요가 없습니다
4. **삭제가 안전합니다.** 백엔드 개발자가 CSS에서 가장 스트레스받는 지점입니다

**다른 선택도 충분히 합리적입니다.** 팀에 CSS를 잘 아는 사람이 있고 디자인 시스템이 이미 있다면 CSS Modules가 나을 수 있습니다. 이 문서의 선택은 "이 독자에게 진입 비용이 가장 낮은 것"입니다.

## 실무 감각 몇 가지

```tsx
{/* ① 기본 — 유틸리티를 나열한다 */}
<div className="rounded p-4 bg-white" />

{/* ② 상태 — 접두사를 붙인다 */}
<button className="bg-blue-600 hover:bg-blue-700 disabled:opacity-50" />

{/* ③ 반응형 — 접두사를 붙인다. 접두사가 없는 쪽이 모바일 */}
<div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-4" />

{/* ④ 조건부 — 문자열을 골라 넣는다 */}
<div className={isActive ? "rounded p-4 bg-blue-50" : "rounded p-4"} />
```

②와 ③이 이 문법의 핵심입니다. 14장의 미디어 쿼리가 `md:`, `lg:` 접두사로 바뀐 것뿐이고 분기점 값도 같습니다.

④처럼 조건부 클래스가 늘어나면 문자열이 지저분해집니다. 그래서 실무에서는 `clsx`나 `tailwind-merge` 같은 작은 라이브러리를 조합해 `cn()` 같은 헬퍼를 하나 만들어 씁니다. **Tailwind에 내장된 것이 아니라 팀이 직접 만드는 관례** 이니, 남의 코드에서 `cn(...)`을 보면 그런 헬퍼라고 생각하시면 됩니다.

> **주의**: 클래스 이름을 문자열로 조립하면 Tailwind가 못 찾아냅니다. `` `text-${color}-500` `` 은 빌드에서 누락됩니다. **완성된 클래스 이름을 통째로 골라 넣으세요.**

## 흔한 오해

**"Tailwind는 인라인 스타일과 같다"**
다릅니다. 인라인 스타일로는 `hover`, 미디어 쿼리, 다크 모드를 쓸 수 없습니다. 그리고 Tailwind는 기본적으로 디자인 시스템 안의 정해진 값을 쓰게 유도합니다(원하면 임의 값도 쓸 수 있지만, 그건 예외로 두는 게 좋습니다).

**"클래스가 길면 성능이 나쁘다"**
CSS 파일은 오히려 훨씬 작아집니다. HTML이 조금 길어지지만 gzip에서 반복 문자열은 잘 압축됩니다.

**"Tailwind를 쓰면 CSS를 몰라도 된다"**
반대입니다. `flex`, `grid`, `absolute`가 무슨 뜻인지 모르면 클래스를 고를 수 없습니다. **13~14장이 여전히 필요합니다.** Tailwind는 CSS를 대체하는 게 아니라 **이름 짓기와 파일 관리** 를 대체합니다.

## 핵심 3가지

- **CSS는 구조적으로 전역입니다.** 이름이 충돌하고, 무엇이 쓰이는지 알 수 없고, 로드 순서가 결과를 바꿉니다. 여기서 세 가지 고통이 나옵니다.
- **해법은 순서대로 발전했습니다.** BEM(규율) → CSS Modules(빌드가 이름 변경) → CSS-in-JS(JS로 작성) → Tailwind(이름을 안 지음).
- **Tailwind는 CSS를 대체하지 않습니다.** 이름 짓기와 파일 관리를 대체할 뿐입니다. 박스 모델과 레이아웃은 여전히 알아야 합니다.
