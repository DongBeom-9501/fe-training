# 13. CSS 기초 — 박스 모델, 캐스케이드, 특이성

> **이 장의 질문**: 스타일을 분명히 줬는데 안 먹는다. 누가 이기는지는 무엇이 정하는가?

## BE로 치면 이런 것

Spring 설정을 떠올려 보세요. 같은 프로퍼티가 `application.yml`, 프로파일별 파일, 환경변수, 커맨드라인 인자에 동시에 있을 수 있습니다. 그러면 **정해진 우선순위** 에 따라 하나가 이깁니다. 그 순서를 모르면 "설정을 바꿨는데 왜 안 먹지?"로 반나절을 씁니다.

CSS가 정확히 그것입니다. 여러 규칙이 같은 요소에 동시에 적용될 수 있고, **누가 이기는지를 정하는 규칙 체계** 가 있습니다. 그 체계의 이름이 **캐스케이드(cascade)** 이고, CSS의 C가 그 C입니다.

CSS가 어려운 이유는 속성이 많아서가 아닙니다. **이 우선순위와 다음 장의 레이아웃 모델, 두 가지 때문입니다.**

## 선택자 — 최소한만

```css
.btn            { }   /* 클래스 — 실무에서 95% */
#header         { }   /* id — 특이성이 너무 높아 잘 안 씀 */
button          { }   /* 태그 — 전역 기본값 정할 때만 */

.card .title    { }   /* 자손 (모든 하위) */
.card > .title  { }   /* 직계 자식만 */

.btn:hover      { }   /* 상태 */
.btn:disabled   { }
tr:nth-child(even) { }

.btn[data-variant="danger"] { }   /* 속성 */
```

**실무에서는 클래스만 쓰는 것이 기본** 입니다. 이유는 다음 절에서 나옵니다.

## 캐스케이드 — 누가 이기는가

여러 규칙이 충돌하면 이 순서로 결정됩니다. **위에서부터 판정하고, 결판나면 아래는 안 봅니다.**

```
0. 요소에 직접 쓴 인라인 스타일인가   (style="...")
1. !important 가 붙었는가
2. 특이성(specificity)이 높은가
3. 나중에 선언됐는가
```

> 실제 CSS 명세의 판정 순서는 이보다 깁니다. 브라우저 기본 스타일과의 우선순위, `@layer`로 만든 계층 등이 앞쪽에 더 있습니다. 다만 **직접 쓴 CSS 안에서 벌어지는 충돌은 위 네 단계로 거의 다 설명됩니다.** 나머지는 필요할 때 찾아보면 됩니다.

### 1단계: `!important`

```css
.btn { color: red !important; }
```

무조건 이깁니다. 그래서 **쓰면 안 됩니다.** 한 번 쓰면 그걸 이기려고 또 `!important`를 쓰게 되고, 결국 아무도 무엇이 적용될지 예측할 수 없게 됩니다. 백엔드로 치면 모든 메서드를 `synchronized`로 막아버리는 것과 비슷한 종류의 해결입니다.

### 2단계: 특이성

선택자마다 점수가 있습니다. `(id, class, tag)` 세 자리 숫자라고 생각하면 됩니다.

| 선택자 | 점수 | |
| --- | --- | --- |
| `button` | (0,0,1) | 태그 1개 |
| `.btn` | (0,1,0) | 클래스 1개 |
| `.card .btn` | (0,2,0) | 클래스 2개 |
| `#save` | (1,0,0) | id 1개 |
| `#save .btn` | (1,1,0) | |

**앞자리가 큰 쪽이 무조건 이깁니다.** 클래스를 백 개 겹쳐도 id 하나를 못 이깁니다.

```css
#save      { color: blue; }    /* (1,0,0) — 이긴다 */
.btn.large.primary { color: red; }  /* (0,3,0) */
```

이것이 **id 선택자를 쓰지 않는 이유** 입니다. 한 번 id로 스타일을 주면 나중에 클래스로 덮어쓸 수 없어서, 결국 `!important`로 가게 됩니다.

> **실무 규칙**: 특이성을 **낮고 평평하게** 유지하세요. 클래스 하나짜리 선택자를 기본으로 쓰고, 중첩을 최소화합니다. 그러면 나중에 덮어쓰기가 쉽습니다.

### 3단계: 선언 순서

특이성이 같으면 **나중에 쓴 것이 이깁니다.** 파일 안에서의 순서, 그리고 파일이 로드된 순서 모두 해당됩니다.

```css
.btn { color: red; }
.btn { color: blue; }   /* 이긴다 */
```

이 규칙 때문에 **CSS 파일의 import 순서가 결과를 바꿉니다.** 15장에서 다룰 문제의 씨앗입니다.

## 상속 — 자동으로 내려가는 것들

일부 속성은 부모에서 자식으로 자동으로 내려갑니다.

```
내려간다:    color, font-family, font-size, line-height, text-align
안 내려간다:  margin, padding, border, background, width, display
```

**글자 관련은 내려가고, 박스 관련은 안 내려간다** 고 외우면 대체로 맞습니다. 그래서 `body`에 폰트를 한 번 지정하면 전체에 적용됩니다.

## 박스 모델 — 모든 요소는 상자다

```
┌─────────────────────────────────┐
│  margin  (바깥 여백, 투명)        │
│  ┌───────────────────────────┐  │
│  │  border  (테두리)          │  │
│  │  ┌─────────────────────┐  │  │
│  │  │  padding (안쪽 여백)  │  │  │
│  │  │  ┌───────────────┐  │  │  │
│  │  │  │   content     │  │  │  │
│  │  │  └───────────────┘  │  │  │
│  │  └─────────────────────┘  │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

여기서 **가장 많이 당하는 함정** 이 있습니다.

```css
.box { width: 200px; padding: 20px; border: 1px solid; }
```

이 요소의 실제 너비는 몇일까요? **242px입니다.** 기본 설정에서 `width`는 content만 가리키고, padding과 border는 그 바깥에 더해지기 때문입니다.

직관에 어긋나서, 현대 CSS에서는 이걸 전역으로 끕니다.

```css
/* 거의 모든 프로젝트가 이 줄로 시작한다 */
*, *::before, *::after { box-sizing: border-box; }
```

이러면 `width: 200px`이 **padding과 border를 포함한 전체 너비** 가 됩니다. Tailwind 같은 도구는 기본으로 켜 줍니다.

### margin 겹침

또 하나의 함정. **위아래 margin은 서로 합쳐지지 않고 큰 쪽 하나만 적용됩니다.**

```css
.a { margin-bottom: 20px; }
.b { margin-top: 30px; }
/* .a와 .b 사이 간격은 50px이 아니라 30px */
```

좌우는 겹치지 않고 위아래만 겹칩니다. 규칙이 복잡해서, 요즘은 **margin 대신 부모의 `gap`으로 간격을 주는 방식** 을 씁니다(14장). 그러면 이 문제 자체가 사라집니다.

## display — 요소의 성격

```css
display: block;         /* 한 줄 다 차지. width/height 적용됨. div, p, h1 */
display: inline;        /* 글자처럼 흐름. width/height 무시됨. span, a */
display: inline-block;  /* 흐르지만 크기 지정 가능 */
display: flex;          /* 자식들을 1차원 배치 (14장) */
display: grid;          /* 자식들을 2차원 배치 (14장) */
display: none;          /* 렌더 트리에서 제거 (입문 5장) */
```

**`inline` 요소에 `width`나 `height`를 줬는데 안 먹는다** — 아주 흔한 질문이고, 답은 "inline이라서"입니다.

## position — 흐름에서 빼내기

```css
position: static;    /* 기본값. 문서 흐름대로 */
position: relative;  /* 흐름은 유지하되 자기 자리에서 이동. 자식의 기준점이 됨 */
position: absolute;  /* 흐름에서 제거. position이 static이 아닌 가장 가까운 조상 기준 */
position: fixed;     /* 흐름에서 제거. 화면(viewport) 기준. 고정 헤더 */
position: sticky;    /* 스크롤하다 특정 지점에서 고정 */
```

**`absolute`의 기준점은 `position`이 `static`이 아닌 가장 가까운 조상** 입니다. `relative`가 대표적이라 이 짝을 가장 많이 쓰지만, `absolute`나 `fixed` 조상도 기준이 됩니다. 그런 조상이 하나도 없으면 페이지 전체가 기준이 되어 엉뚱한 곳에 붙습니다.

```css
.card    { position: relative; }
.badge   { position: absolute; top: 8px; right: 8px; }  /* 카드 우상단 */
```

> `position: absolute`로 레이아웃 전체를 짜려는 유혹이 있는데, 반응형에서 무너집니다. **레이아웃은 Flex/Grid로, `absolute`는 뱃지·툴팁·오버레이 같은 국소적인 것에만** 쓰세요.

## 단위

| 단위 | 기준 | 쓰는 곳 |
| --- | --- | --- |
| `px` | 절대 | 테두리, 그림자, 미세 조정 |
| `rem` | 루트 폰트 크기(보통 16px) | **간격, 폰트 크기 — 기본으로 쓰세요** |
| `em` | 부모 폰트 크기 | 중첩되면 누적돼서 헷갈림. 피하는 편 |
| `%` | 부모 크기 | 너비 |
| `vw` / `vh` | 화면 너비/높이의 1% | 전체 화면 요소 |

**`rem`을 기본으로 쓰는 이유**: 사용자가 브라우저 기본 글자 크기를 키우면 `rem`으로 만든 것들은 전부 같이 커집니다. `px`로 고정하면 커지지 않습니다. 접근성 문제입니다.

## 흔한 오해

**"CSS는 순서대로 위에서 아래로 적용된다"**
순서는 마지막 판정 기준입니다. 특이성이 먼저입니다.

**"안 먹으면 `!important`를 붙이면 된다"**
당장은 해결되고 나중에 더 큰 비용으로 돌아옵니다. 개발자 도구에서 **어떤 규칙이 이겼는지 취소선으로 보여줍니다.** 거기서 원인을 찾으세요.

**"`width: 100%`면 부모에 딱 맞는다"**
`box-sizing: border-box`가 없으면 padding만큼 넘칩니다.

**"margin으로 간격을 주는 게 정석이다"**
겹침 규칙 때문에 예측이 어렵습니다. 부모의 `gap`이 더 낫습니다.

## 핵심 3가지

- **누가 이기는지에 규칙이 있습니다.** 인라인 스타일 → `!important` → 특이성 → 선언 순서 순으로 판정합니다. 특이성을 낮고 평평하게 유지해야 나중에 덮어쓸 수 있습니다.
- **모든 요소는 상자입니다.** 기본 설정에서 `width`는 content만 가리킵니다. 그래서 거의 모든 프로젝트가 `box-sizing: border-box`를 켭니다.
- **레이아웃은 Flex/Grid로.** `position: absolute`는 뱃지나 툴팁 같은 국소적 용도에만 씁니다. 간격은 `gap`으로 주세요.
