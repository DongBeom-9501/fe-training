# 2. BE와 FE의 근본적 차이 — 상태를 누가, 얼마나 오래 들고 있는가

> **이 장의 질문**: 나는 이미 서버를 잘 만든다. 프론트엔드는 대체 무엇이 그렇게 다른가?

이 문서에서 가장 중요한 장입니다. 여기서 심는 통찰 하나가 앞으로 나올 어려움의 대부분을 미리 설명해 줍니다.

## BE로 치면 이런 것

당신이 만든 API 서버를 떠올려 보세요.

요청이 들어온다 → 컨트롤러가 받는다 → 서비스가 처리한다 → 응답을 내보낸다 → **끝난다.**

그리고 다음 요청은 처음부터 다시 시작합니다. 서버는 직전 요청이 무엇을 했는지 기억하지 않습니다. 기억해야 할 것은 전부 DB나 Redis로 밀어 넣었으니까요.

이 "기억하지 않는다"가 백엔드를 다루기 쉽게 만드는 핵심입니다. 인스턴스를 몇 개로 늘리든 상관없고, 하나가 죽어도 다른 게 받으면 되고, 배포는 그냥 갈아끼우면 됩니다. 요청의 수명이 짧기 때문에 가능한 일입니다.

**프론트엔드에는 그게 없습니다.**

## 문제 상황

사용자가 관리자 대시보드를 엽니다. 그리고 **세 시간 동안 그 탭을 닫지 않습니다.**

그 세 시간 동안 이런 일이 벌어집니다.

- 목록을 필터링하고, 정렬을 바꾸고, 3페이지로 갑니다
- 상세 모달을 열어 뭔가를 수정하다가, 저장하지 않고 닫습니다
- 다른 탭에 갔다가 돌아옵니다
- 옆자리 동료가 같은 데이터를 수정합니다
- 로그인 토큰이 만료됩니다
- 노트북 뚜껑을 덮었다가 다음 날 아침에 엽니다

이 모든 것을 겪는 동안 **당신의 JavaScript 코드는 한 번도 죽지 않았습니다.** 처음 로드될 때 만들어진 그 프로세스가, 그 메모리가, 그 변수들이 세 시간째 살아 있습니다.

서버로 치면 이건 요청 하나가 세 시간 동안 살아 있으면서 그 안에 온갖 상태를 들고 있는 것과 같습니다. 백엔드에서라면 절대 이렇게 짜지 않을 코드입니다. 그런데 프론트엔드에서는 이게 **기본값** 입니다.

## 핵심 개념: 수명의 차이

```
[백엔드]  요청 → 처리 → 응답 → 소멸        (수명: 밀리초)
          요청 → 처리 → 응답 → 소멸
          요청 → 처리 → 응답 → 소멸
              ↑ 상태는 전부 바깥(DB/Redis)에

[프론트엔드]  로드 ────────────────────────→ 탭 닫힘   (수명: 수 시간)
                 ↑ 상태가 그 안(메모리)에 계속 쌓임
```

백엔드가 상태를 **밖으로 밀어내서** 문제를 푼다면, 프론트엔드는 상태를 **안에 들고 있으면서** 문제를 풉니다. 밀어낼 곳이 없기 때문입니다. 화면에 지금 무엇이 열려 있고, 어떤 필터가 걸려 있고, 사용자가 어디까지 입력했는지는 서버가 알 바가 아닙니다.

### 여기서 파생되는 네 가지 어려움

이 문서 뒤쪽에서 만날 어려운 주제들은 사실상 전부 여기서 나옵니다.

| 어려움 | 왜 생기나 | 어디서 다루나 |
| --- | --- | --- |
| **상태 관리** | 오래 사는 프로세스 안에 상태가 계속 쌓입니다. 어떤 상태를 어디에 둘지 설계해야 합니다 | 33장 |
| **리렌더링** | 상태가 바뀌면 화면의 어느 부분을 다시 그릴지 결정해야 합니다 | 18장 |
| **캐시 무효화** | 세 시간 전에 받아온 데이터가 아직 화면에 떠 있습니다. 언제 다시 받아올까요? | 34장 |
| **메모리 누수** | 죽지 않는 프로세스라서, 정리하지 않은 것은 계속 쌓입니다 | 19장 |

지금 이 네 가지를 이해할 필요는 없습니다. 다만 **뒤에서 이게 나오면 "아, 프로세스가 오래 살아서 그런 거구나"라고 떠올릴 수 있으면** 이 장은 성공입니다.

## 두 번째 차이: 신뢰 경계

백엔드 코드는 당신의 서버에서 돕니다. 코드도, 메모리도, 환경변수도 당신 것입니다.

프론트엔드 코드는 **사용자의 컴퓨터에서 돕니다.** 그래서 이런 것들이 전부 참입니다.

- 사용자는 당신의 소스 코드를 전부 읽을 수 있습니다 (개발자 도구 → Sources)
- 사용자는 어떤 값이든 바꿔서 요청을 보낼 수 있습니다
- 사용자는 당신이 숨긴 버튼을 다시 보이게 만들 수 있습니다
- 프론트엔드에 넣은 "비밀"은 비밀이 아닙니다

여기서 실무 규칙 하나가 나옵니다. **프론트엔드의 검증은 UX이고, 보안은 서버의 몫입니다.**

이메일 형식 검사, 필수값 체크, 권한에 따른 메뉴 숨김 — 이것들은 사용자를 편하게 해주려고 하는 것이지, 막으려고 하는 게 아닙니다. 진짜로 막는 건 서버에서 다시 해야 합니다. 이건 당신이 이미 아는 이야기지만, 프론트엔드 코드를 볼 때 계속 떠올려야 하는 이야기이기도 합니다.

> 37장(API 레이어와 인증), 27장(프론트엔드 보안)에서 다시 만납니다.

## 세 번째 차이: 실행 환경이 하나가 아니다

당신의 서버는 당신이 정한 환경에서 돕니다. JDK 버전도, 메모리도, OS도 당신이 정합니다.

프론트엔드 코드는 이 모든 조합 위에서 동시에 돌아야 합니다.

- 27인치 모니터와 5년 된 저가 안드로이드 폰
- 최신 크롬과 회사 정책 때문에 고정된 구버전 브라우저
- 기가비트 사내망과 지하철 LTE
- 마우스, 손가락, 키보드만 쓰는 사용자, 스크린 리더

그래서 프론트엔드에는 백엔드에 없는 종류의 요구사항이 생깁니다. **반응형**(화면 크기), **접근성**(입력 수단), **성능 예산**(느린 기기와 느린 망). 각각 14장, 12장, 24장에서 다룹니다.

## 그래서 겹치는 것과 다른 것

| | 백엔드 | 프론트엔드 |
| --- | --- | --- |
| 코드 수명 | 요청 단위 (ms) | 세션 단위 (시간) |
| 상태 위치 | 바깥 (DB, Redis) | 안 (메모리) — 그리고 URL, 서버 |
| 실행 주체 | 내 서버 | 사용자 기기 |
| 동시성 | 멀티 스레드 / 코루틴 | **싱글 스레드** (6장) |
| 배포 후 | 즉시 새 코드 | 사용자가 새로고침할 때까지 옛 코드 |
| 실패 처리 | 재시도, 서킷 브레이커 | 그 화면에서 사용자에게 보여주기 |
| 테스트 | 대체로 결정적 | 브라우저·타이밍 의존 |

**하지만 겹치는 것이 더 많습니다.** 관심사 분리, 의존성 방향, 이름 짓기, 테스트 가능한 설계, 도메인 모델링 — 당신이 5년 동안 쌓은 이것들은 전부 그대로 통합니다. 실제로 프론트엔드 코드베이스가 망가지는 이유 대부분은 React를 몰라서가 아니라 **설계를 안 해서** 입니다. 그 부분에서 당신은 이미 유리합니다.

## 흔한 오해

**"프론트엔드는 화면 그리는 거니까 쉽다"**
화면을 그리는 것 자체는 쉽습니다. 어려운 건 세 시간 동안 살아 있는 상태를 일관되게 유지하는 것입니다. 그리고 그건 분산 시스템 문제와 성질이 비슷합니다.

**"백엔드를 알면 프론트엔드는 금방 한다"**
문법은 금방 합니다. 대신 처음에 거의 모두가 같은 실수를 합니다 — **서버에서 받아온 데이터를 로컬 상태로 복사해서 관리하는 것.** 왜 그게 문제인지는 26–34장에서 다룹니다. 지금은 "그런 함정이 있다"만 기억하세요.

**"상태 관리 라이브러리부터 배워야겠다"**
아닙니다. 상태에는 종류가 있고(서버/클라이언트/URL/폼), 대부분의 상태는 라이브러리 없이 제자리에 두는 게 맞습니다. 33장에서 분류부터 합니다.

## 핵심 3가지

- **수명이 다릅니다.** 백엔드 코드는 요청과 함께 태어나 응답과 함께 죽습니다. 프론트엔드 코드는 탭이 열려 있는 몇 시간 동안 계속 살아 있습니다.
- **그래서 어려운 것들이 생깁니다.** 상태 관리, 리렌더링, 캐시 무효화, 메모리 누수. 전부 이 수명 차이에서 나옵니다.
- **코드가 남의 기기에서 돕니다.** 그래서 프론트엔드의 검증은 UX일 뿐이고, 보안은 여전히 서버의 몫입니다.
