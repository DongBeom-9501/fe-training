# 25. 렌더링 성능 — 리렌더 추적과 memo의 함정

> **이 장의 질문**: 화면이 버벅인다. React 코드에서 어디를 봐야 하는가?

## BE로 치면 이런 것

느린 API를 만나면 당신은 뭘 먼저 합니까. 코드를 고치지 않습니다. **`EXPLAIN`을 찍고 실행 계획을 봅니다.** 인덱스를 안 타는지, N+1이 도는지 확인한 다음에 고칩니다.

프론트엔드에도 `EXPLAIN`이 있습니다. **React DevTools Profiler** 입니다.

이 장의 제1 규칙은 백엔드와 같습니다.

> **재기 전에 고치지 마세요.**

측정 없이 `memo`와 `useMemo`를 뿌리는 것은 모든 컬럼에 인덱스를 거는 것과 같습니다. 쓰기가 느려지고 코드는 지저분해지는데, 정작 느린 쿼리는 그대로입니다.

## 먼저: 리렌더는 대개 문제가 아니다

18장에서 봤듯 렌더에는 세 단계가 있습니다.

```
① 렌더    컴포넌트 함수 실행 → 새 설명서            싸다
② 재조정  이전 설명서와 비교                        싸다
③ 커밋    달라진 만큼 실제 DOM 수정                 비싸다
```

**리렌더가 100번 일어나도 결과가 같으면 ③은 0번입니다.** 그러니 "리렌더가 일어난다"는 사실 자체는 경보가 아닙니다.

문제가 되는 건 딱 세 경우입니다.

| 증상 | 원인 |
| --- | --- |
| 렌더 한 번이 오래 걸림 | 렌더 함수 안에 무거운 계산이 있음 |
| 렌더가 너무 자주 일어남 | 상태가 필요 이상으로 위에 있음 |
| 한 번에 그릴 것이 너무 많음 | 수천 개 행을 한꺼번에 렌더 |

**해법이 각각 다릅니다.** 그래서 무엇인지부터 알아야 합니다.

## 측정 — React DevTools Profiler

브라우저 확장 **React Developer Tools** 를 설치하면 Profiler 탭이 생깁니다.

**쓰는 법**

1. Profiler 탭 → 녹화 시작
2. 느리다고 느끼는 동작을 실제로 해봅니다
3. 녹화 중지

**보는 법**

- **가로 막대의 길이** = 그 컴포넌트 렌더에 걸린 시간
- **회색 막대** = 이번에 렌더되지 않은 컴포넌트
- 컴포넌트를 클릭하면 **왜 렌더됐는지** 가 나옵니다 (설정에서 "Record why each component rendered" 켜기)

이유는 대개 이 넷 중 하나입니다.

```
Props changed          부모가 다른 값을 내려줬다
Hook changed           useState/useContext 값이 바뀌었다
Parent rendered        부모가 렌더돼서 따라 내려왔다
Context changed        구독 중인 Context 값이 바뀌었다
```

> **가장 먼저 볼 것**: 오래 걸린 막대 하나를 찾으세요. 짧은 막대 수백 개보다 긴 막대 하나가 대개 진짜 원인입니다.

## 원인 1: 렌더 안의 무거운 계산

```tsx
// ❌ 렌더될 때마다 1만 건을 정렬한다. 타이핑 한 글자마다.
function OrderTable({ orders, keyword }) {
  const sorted = [...orders].sort((a, b) => b.amount - a.amount);
  const filtered = sorted.filter(o => o.id.includes(keyword));
  return <Table rows={filtered} />;
}
```

`keyword`가 바뀔 때마다 정렬까지 다시 합니다. 정렬 결과는 `keyword`와 무관한데도요.

**해법: `useMemo`**

```tsx
// ✅ orders가 바뀔 때만 정렬을 다시 한다
const sorted = useMemo(
  () => [...orders].sort((a, b) => b.amount - a.amount),
  [orders]
);
const filtered = sorted.filter(o => o.id.includes(keyword));   // 필터는 싸니 그냥
```

`useMemo`는 **의존성이 그대로면 지난번 결과를 그대로 돌려줍니다.** 계산 결과를 캐시하는 것입니다.

> **그런데 대부분의 계산에는 필요 없습니다.** 배열 100개를 필터하는 건 0.01ms입니다. `useMemo` 자체도 비교와 저장 비용이 있어서, 싼 계산에 붙이면 손해입니다. **재보고 오래 걸리는 것에만 붙이세요.**

## 원인 2: 렌더가 너무 자주 일어난다

```tsx
// ❌ 타이핑 한 글자마다 페이지 전체가 렌더된다
function OrderPage() {
  const [keyword, setKeyword] = useState('');
  return (
    <>
      <input value={keyword} onChange={e => setKeyword(e.target.value)} />
      <HugeTable orders={orders} />   {/* keyword와 무관한데 같이 렌더됨 */}
    </>
  );
}
```

**해법의 순서가 중요합니다.**

### 먼저: 상태를 아래로 내린다 (20장)

```tsx
// ✅ 타이핑 상태를 작은 컴포넌트 안에 가둔다
function OrderPage() {
  const [applied, setApplied] = useState('');
  return (
    <>
      <SearchBox onSubmit={setApplied} />   {/* 타이핑은 이 안에서만 */}
      <HugeTable orders={orders} keyword={applied} />
    </>
  );
}
```

**구조로 푸는 것이 항상 먼저입니다.** 메모이제이션은 구조를 못 바꿀 때 쓰는 차선책입니다.

### 그 다음: `memo`

```tsx
// props가 지난번과 같으면 렌더를 건너뛴다
const HugeTable = memo(function HugeTable({ orders, keyword }) { ... });
```

`memo`는 **props를 이전과 비교해서 같으면 함수 실행을 건너뜁니다.** 비교는 얕은 비교입니다 — 각 prop을 `Object.is`로 봅니다.

**여기에 함정이 있습니다.**

## `memo`의 함정

```tsx
// ❌ memo를 붙였는데 전혀 효과가 없다
const Row = memo(function Row({ order, onSelect }) { ... });

function Table({ orders }) {
  return orders.map(o => (
    <Row
      key={o.id}
      order={o}
      onSelect={() => select(o.id)}   {/* ← 매 렌더마다 새 함수 */}
      style={{ padding: 8 }}          {/* ← 매 렌더마다 새 객체 */}
    />
  ));
}
```

`onSelect`와 `style`은 **렌더될 때마다 새로 만들어집니다**(심화 가이드 3장의 그 이야기). 참조가 매번 다르니 `memo`의 비교는 항상 "다르다"로 끝납니다.

**`memo`는 일하고 있고, 아무것도 막지 못합니다.** 순수한 손해입니다.

**해법: 참조를 고정한다**

```tsx
const handleSelect = useCallback((id: string) => select(id), []);
const rowStyle = useMemo(() => ({ padding: 8 }), []);
```

`useCallback`은 함수 버전의 `useMemo`입니다. `useCallback(fn, deps)`는 `useMemo(() => fn, deps)`와 같습니다.

> **여기서 중요한 결론이 나옵니다.** `memo`는 혼자 쓰면 대개 무용지물입니다. **자식에게 내려가는 모든 객체·함수 props의 참조를 고정해야** 비로소 동작합니다. 그래서 비용이 셋으로 늘어납니다 — `memo` + `useCallback` + `useMemo`, 그리고 그것들의 의존성 배열 관리.
>
> **이 비용을 치를 값어치가 있는지 재본 다음에 하세요.**

## `useCallback`을 언제 쓰나

세 경우뿐입니다.

1. `memo`가 걸린 자식에게 함수를 내려줄 때
2. `useEffect`의 의존성 배열에 함수가 들어갈 때 (19장의 무한 루프)
3. 커스텀 훅이 함수를 반환할 때 (쓰는 쪽이 의존성에 넣을 수 있으므로)

**그 외에는 붙이지 마세요.** 그냥 함수를 만드는 비용은 사실상 0입니다.

## 원인 3: 한 번에 너무 많이 그린다

```tsx
// ❌ 5000행을 전부 DOM에 만든다
{orders.map(o => <OrderRow key={o.id} order={o} />)}
```

`memo`로도 `useMemo`로도 해결되지 않습니다. **DOM 노드 5000개를 실제로 만드는 비용** 이기 때문입니다. 레이아웃 계산도 5000개분 일어납니다(5장).

**해법: 가상 스크롤**

화면에 보이는 20행 정도만 실제로 그리고, 나머지는 빈 공간의 높이로만 표현합니다. 스크롤하면 그 자리에 들어갈 것을 새로 그립니다.

`@tanstack/react-virtual` 같은 라이브러리를 씁니다.

> **판단 기준**: 수백 행까지는 그냥 그려도 됩니다. **1000행을 넘어가면** 가상 스크롤을 검토하세요. 그 전에 "정말 1000행을 한 번에 보여줘야 하는가"(페이지네이션으로 충분한가)를 먼저 묻는 게 낫습니다.

## 리스트에서 가장 흔한 진짜 원인

성능 문제로 보고된 것의 상당수가 사실 이것입니다.

```tsx
{orders.map((o, i) => <OrderRow key={i} ... />)}   // ❌
```

18장에서 다룬 인덱스 `key`입니다. 목록이 바뀔 때 React가 엉뚱한 컴포넌트를 재사용하면서 **불필요한 DOM 조작이 대량으로 발생합니다.** 게다가 상태까지 어긋납니다.

**`key`를 고치는 것이 어떤 메모이제이션보다 효과가 큽니다.** 성능 이슈를 받으면 여기부터 보세요.

## React Compiler

React 19와 함께 나온 컴파일러입니다. **빌드 시점에 코드를 분석해서 `useMemo`·`useCallback`·`memo`에 해당하는 최적화를 자동으로 넣어 줍니다.**

적용되면 이 장의 손 최적화를 상당 부분 안 해도 됩니다. 다만 **컴포넌트가 순수해야** 동작합니다(심화 가이드 3장). 렌더 중에 props를 수정하거나 외부 변수를 건드리는 코드가 있으면 컴파일러가 최적화를 포기합니다.

> **지금 할 일**: 컴파일러를 쓰든 안 쓰든, **순수하게 쓰는 습관** 이 그대로 이득이 됩니다. 도입 여부는 프로젝트 상황에 따라 판단하세요.

## 진단 순서 정리

```
1. Profiler로 녹화한다                      ← 여기부터. 예외 없음
2. 긴 막대 하나를 찾는다
3. "왜 렌더됐나"를 본다
   ├─ 렌더 자체가 오래 걸림  → 무거운 계산? useMemo
   ├─ 너무 자주 렌더됨       → 상태를 아래로. 안 되면 memo + useCallback
   └─ 그릴 게 너무 많음      → key 확인 → 페이지네이션 → 가상 스크롤
4. 다시 재서 실제로 나아졌는지 확인한다
```

## 흔한 오해

**"memo를 많이 붙일수록 빠르다"**
비교 비용이 생기고, 참조를 고정하지 않으면 효과가 0입니다. 재고 붙이세요.

**"useMemo는 공짜다"**
의존성 배열 비교와 값 저장에 비용이 있습니다. 싼 계산에는 손해입니다.

**"리렌더를 0으로 만들어야 한다"**
목표가 아닙니다. 목표는 **사용자가 느끼는 지연** 을 없애는 것입니다(24장의 INP).

**"React가 느려서 성능이 안 나온다"**
실무에서 만나는 원인은 대부분 인덱스 `key`, 첫 화면 번들 크기(22장), 이미지(26장)입니다.

## 핵심 3가지

- **재기 전에 고치지 마세요.** Profiler로 녹화하고, 긴 막대를 찾고, 왜 렌더됐는지 봅니다. 백엔드에서 `EXPLAIN` 없이 인덱스를 걸지 않는 것과 같습니다.
- **원인에 따라 해법이 다릅니다.** 렌더가 느리면 `useMemo`, 너무 자주 렌더되면 상태를 아래로(그다음이 `memo`), 그릴 게 많으면 가상 스크롤.
- **`memo`는 혼자서는 무용지물입니다.** 내려가는 객체·함수 props의 참조를 고정해야 동작합니다. 그 비용을 치를 값어치가 있는지 먼저 재세요.
