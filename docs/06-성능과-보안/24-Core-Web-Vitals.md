# 24. Core Web Vitals — FE의 SLI/SLO

> **이 장의 질문**: "화면이 느리다"를 감이 아니라 숫자로 말하려면 무엇을 재야 하는가?

## BE로 치면 이런 것

당신은 이미 이렇게 말합니다.

> "주문 조회 API p99가 200ms를 넘으면 알림이 옵니다."

지표(SLI)를 정하고 목표(SLO)를 걸고 알림을 겁니다. **"느린 것 같다"는 말로 회의를 하지 않습니다.**

프론트엔드에도 같은 체계가 있습니다. 이름이 **Core Web Vitals** 입니다. 이 장은 그 세 지표와, 그것을 재고 지키는 방법입니다.

## 문제 상황: 서버는 빠른데 사용자는 느리다고 한다

3장에서 봤던 상황입니다. API p99가 50ms인데 사용자는 "느리다"고 합니다. 왜일까요.

사용자가 체감하는 시간은 이것들의 합이기 때문입니다.

```
서버 응답 →  HTML 파싱  →  CSS·JS 내려받기  →  JS 실행  →  화면 그리기  →  버튼이 눌리기 시작
   50ms         30ms          800ms            600ms        100ms
   └─ 당신이 재던 구간 ─┘  └────────── 아무도 안 재던 구간 ──────────┘
```

**백엔드 지표는 첫 칸만 봅니다.** 나머지가 훨씬 큰데도요. Core Web Vitals는 이 전체를 사용자 관점에서 세 조각으로 나눠 잽니다.

## 세 지표

각 지표가 사용자의 질문 하나에 대응합니다.

| 지표 | 사용자의 질문 | 좋음 | 나쁨 |
| --- | --- | --- | --- |
| **LCP** | "내용이 보이나?" | ≤ 2.5s | > 4.0s |
| **INP** | "눌렀는데 반응하나?" | ≤ 200ms | > 500ms |
| **CLS** | "누르려는데 밀려나나?" | ≤ 0.1 | > 0.25 |

### LCP — Largest Contentful Paint

**화면에서 가장 큰 요소가 그려지기까지의 시간.** 보통 대표 이미지나 큰 제목입니다.

"뭐라도 보이는 시점"이 아니라 **"이 페이지가 무엇인지 알 수 있는 시점"** 을 재려는 것입니다. 로딩 스피너만 떠 있는 것은 LCP를 좋게 만들어주지 않습니다.

**LCP를 망치는 것들**

| 원인 | 어디서 다루나 |
| --- | --- |
| 서버 응답이 느림 | 백엔드 |
| CSS가 렌더를 막음 | 3장 |
| 큰 이미지를 원본 크기로 내려받음 | 26장 |
| JS를 다 받고 실행해야 내용이 나옴 | 22장, 그리고 **Part 7** |

마지막 항목이 중요합니다. 화면 내용을 **누가 만드느냐** (브라우저의 JS인가, 서버가 만들어 보낸 HTML인가)에 따라 LCP가 크게 달라집니다. 이건 렌더링 전략의 문제라 **28장에서 본격적으로 다룹니다.** 지금은 "여기가 큰 변수"라는 것만 알아두세요.

### INP — Interaction to Next Paint

**사용자가 클릭·입력했을 때, 화면이 반응할 때까지의 시간.** 세션 전체에서 나쁜 쪽을 대표값으로 잡습니다.

6장이 그대로 회수되는 지표입니다. **메인 스레드가 하나뿐이라, 뭔가 오래 붙잡고 있으면 클릭이 큐에서 기다립니다.**

```js
// 이 함수가 400ms 걸리면, 그동안 누른 클릭은 400ms 뒤에 처리된다
function handleFilter() {
  const result = hugeArray.filter(...).sort(...);   // 메인 스레드 점유
  setRows(result);
}
```

**INP를 망치는 것들**

- 렌더 중 무거운 계산 (25장)
- 한 번에 너무 많은 DOM을 그림 (25장)
- 큰 JSON 파싱, 큰 배열 정렬
- 무거운 서드파티 스크립트 (채팅 위젯, 분석 도구)

### CLS — Cumulative Layout Shift

**이미 그려진 요소가 나중에 밀려난 정도.** 시간이 아니라 **누적 점수** 입니다.

읽고 있던 문단이 갑자기 아래로 밀리거나, 누르려던 버튼 위에 배너가 끼어들어 엉뚱한 것을 누르게 되는 그 현상입니다.

**CLS를 망치는 것들과 해법**

| 원인 | 해법 |
| --- | --- |
| 이미지에 크기를 안 줘서 로드 후 자리를 차지 | `width`/`height`를 미리 지정 |
| 폰트가 늦게 와서 글자 크기가 바뀜 | `font-display: optional` 또는 폰트 preload (26장) |
| 광고·배너가 나중에 삽입됨 | 자리를 미리 비워둠 |
| 데이터가 온 뒤 요소가 늘어남 | 스켈레톤을 **실제 높이와 같게** |

> 마지막 항목이 실무에서 자주 놓칩니다. 스켈레톤을 넣었는데 실제 콘텐츠보다 짧으면, 오히려 밀림이 생깁니다. **높이를 맞춰야 의미가 있습니다.**

## 두 종류의 측정 — 이 구분이 핵심입니다

백엔드에서 "부하 테스트 결과"와 "프로덕션 메트릭"을 구분하듯, 프론트엔드에도 둘이 있습니다.

| | 실험실 측정 (Lab) | 실사용자 측정 (RUM) |
| --- | --- | --- |
| 무엇 | 내 기계에서 조건을 고정하고 잼 | 진짜 사용자 브라우저에서 수집 |
| 도구 | Lighthouse, DevTools | `web-vitals` 라이브러리, 분석 도구 |
| 장점 | 재현 가능. 고치면 바로 확인됨 | **진짜 사용자 경험** |
| 한계 | 내 맥북 + 사내 기가망 기준 | 원인 파악이 어려움 |

**둘 다 필요합니다.** 그리고 순서가 있습니다.

> **RUM으로 문제를 발견하고, Lab으로 원인을 찾고, RUM으로 개선을 확인합니다.**

Lighthouse 점수만 보고 최적화하는 것은 **부하 테스트만 보고 프로덕션 성능을 판단하는 것** 과 같습니다. 개발자의 기계는 사용자의 기계보다 훨씬 빠릅니다.

### 실제로 재는 법

**Lab — 지금 당장**

크롬 개발자 도구 → Lighthouse 탭 → 분석 실행. 주의할 점 두 가지입니다.

- **시크릿 창에서 재세요.** 확장 프로그램이 결과를 왜곡합니다
- **CPU/네트워크 스로틀링을 켜세요.** 개발 기계 기준으로는 늘 좋게 나옵니다

**RUM — 코드 몇 줄**

```ts
import { onLCP, onINP, onCLS } from 'web-vitals';

// 각 지표가 확정되면 우리 서버로 보낸다
const send = (metric) => {
  navigator.sendBeacon('/api/vitals', JSON.stringify(metric));
};

onLCP(send);
onINP(send);
onCLS(send);
```

백엔드에서 메트릭을 수집해 대시보드를 만드는 것과 같습니다. `sendBeacon`을 쓰는 이유는 **사용자가 페이지를 떠나는 중에도 전송이 보장되기 때문** 입니다.

## SLO를 어떻게 잡을까

백엔드에서 하던 대로 하면 됩니다. 다만 프론트엔드에서는 **대상을 명시하는 것** 이 특히 중요합니다.

```
❌ "LCP 2.5초 이하"
✅ "실사용자 LCP 75퍼센타일이 모바일에서 2.5초 이하"
```

세 가지를 붙여야 의미가 생깁니다.

1. **실사용자 기준인가, 실험실 기준인가**
2. **퍼센타일** — 평균은 쓰지 않습니다. 백엔드에서 p99를 보는 것과 같은 이유입니다
3. **기기 구분** — 데스크톱과 모바일은 다른 세계입니다. 합쳐서 보면 모바일 문제가 가려집니다

> Core Web Vitals의 공식 기준은 **75퍼센타일** 입니다. "사용자 4명 중 3명은 이 이내"라는 뜻입니다.

## 성능 예산 — 회귀를 막기

한 번 고쳐놔도 다음 기능에서 다시 무거워집니다. 그래서 **CI에서 막습니다.**

```
첫 화면 JS   ≤ 200KB (압축 후)
LCP (Lab)   ≤ 2.5s
```

23장의 파이프라인에 한 줄 더 넣는 셈입니다. 번들 크기가 기준을 넘으면 CI가 실패하게 하면, **성능이 코드 리뷰의 대상이 됩니다.**

백엔드에서 느린 쿼리가 리뷰에서 걸리는 것과 같은 장치입니다.

## 어디부터 손댈까

측정했더니 나쁘다면, 이 순서로 보는 것이 대체로 효율적입니다.

```
1. 첫 화면에 필요 없는 JS를 걷어낸다        → 22장 (코드 스플리팅)
2. 이미지 크기와 포맷을 손본다               → 26장
3. 리렌더와 무거운 계산을 줄인다             → 25장
4. 렌더링 전략 자체를 바꾼다                 → Part 7 (28~32장)
```

**대개 1번과 2번이 가장 큰 효과를 냅니다.** 그런데 개발자들은 3번(코드 최적화)부터 손대는 경향이 있습니다. 재보지 않았기 때문입니다.

## 흔한 오해

**"Lighthouse 점수 100점이 목표다"**
점수는 실험실 조건의 합성값입니다. **실사용자 지표가 진짜입니다.** 100점인데 사용자는 느릴 수 있습니다.

**"평균 LCP를 보면 된다"**
평균은 소수의 아주 나쁜 경험을 가립니다. 퍼센타일을 보세요.

**"성능은 나중에 최적화하면 된다"**
LCP를 결정하는 요인의 상당수는 구조입니다 — 어떤 라이브러리를 쓰는지, 화면을 누가 만드는지. 나중에 바꾸려면 크게 뜯어야 합니다.

**"우리는 사내 어드민이라 성능은 상관없다"**
LCP는 덜 중요할 수 있습니다. 하지만 **INP는 오히려 더 중요합니다.** 하루 종일 그 화면에서 입력하는 사람에게 매 클릭 300ms는 큰 고통입니다.

## 핵심 3가지

- **세 가지를 잽니다.** LCP(보이나), INP(반응하나), CLS(밀리나). 각각 사용자의 질문 하나에 대응합니다.
- **실사용자 측정이 진짜입니다.** Lighthouse는 원인을 찾는 도구이지 목표가 아닙니다. 개발 기계는 사용자 기계보다 빠릅니다.
- **SLO에는 조건을 붙입니다.** "실사용자 · 75퍼센타일 · 모바일" 처럼. 그리고 CI에 성능 예산을 걸어 회귀를 막습니다.
