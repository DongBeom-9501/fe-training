# 26. 네트워크·에셋 최적화와 HTTP 캐싱

> **이 장의 질문**: 화면에 그릴 것이 도착하기까지의 시간을 어떻게 줄이는가?

## BE로 치면 이런 것

당신은 이미 캐시 계층을 설계합니다. Redis에 무엇을 넣을지, TTL을 얼마로 할지, 언제 무효화할지. 그리고 **응답 크기** 도 신경 씁니다 — 불필요한 필드를 빼고, 페이지네이션을 걸고, gzip을 켭니다.

프론트엔드에서는 그 대상이 **JS·CSS·이미지·폰트** 로 바뀝니다. 그리고 캐시가 **사용자 브라우저와 CDN** 두 곳에 있습니다.

25장이 "이미 받은 것으로 화면을 그리는 속도"였다면, 이 장은 **"받는 속도"** 입니다. 24장에서 봤듯 LCP를 결정하는 것은 대개 이쪽입니다.

## 무엇부터 볼까

3장의 워터폴을 다시 떠올리세요. 사용자가 페이지를 열면 요청이 수십 개 나갑니다. 그중 무엇이 큰지는 재보면 바로 나옵니다.

**개발자 도구 → Network 탭 → 캐시 비활성화 → 새로고침.** 크기 순으로 정렬하면 범인이 보입니다. 대개 이 순서입니다.

```
1. 이미지        가장 큰 경우가 압도적으로 많음
2. JavaScript    번들
3. 폰트
4. CSS
```

**그런데 개선 우선순위는 다릅니다.** 크기가 아니라 **첫 화면을 막는지** 로 판단해야 합니다.

## 이미지 — 가장 큰 효과, 가장 쉬운 작업

### 크기부터

가장 흔한 실수입니다. 4000×3000 원본 사진을 300px 자리에 넣습니다.

```html
<!-- ❌ 4MB를 받아서 300px로 줄여서 보여준다 -->
<img src="/photo.jpg" width="300" />
```

브라우저는 **원본 전체를 다 받은 뒤에** 줄입니다. 필요한 것보다 100배 큰 데이터를 받은 셈입니다.

**표시될 크기에 맞춰 미리 줄여서 서빙하세요.** 화면 밀도를 감안해 2배까지가 실용적인 상한입니다.

### 포맷

| 포맷 | 언제 |
| --- | --- |
| **WebP** | 사진·그래픽 모두 무난. 호환성 좋음. **기본 선택** |
| **AVIF** | 같은 화질에서 더 작아지는 경우가 많음. 인코딩이 느림 |
| JPEG | 폴백용 |
| PNG | 글자·도형처럼 경계가 또렷한 그림에 유리 (무손실) |
| **SVG** | 아이콘·로고. 확대해도 안 깨지고 대개 아주 작음 |

> 압축 결과는 **이미지 내용과 화질 설정에 따라 달라집니다.** 순위를 외우지 말고 실제로 바꿔서 크기를 비교하세요. 투명도는 WebP와 AVIF도 지원합니다.

사진 하나가 JPEG 800KB에서 WebP 300KB로 줄어드는 식입니다(이미지에 따라 다릅니다). **작업량 대비 효과가 가장 큰 항목입니다.**

### 지연 로딩

```html
<!-- 화면 밖 이미지는 스크롤이 가까워질 때 받는다 -->
<img src="/thumb.webp" loading="lazy" width="300" height="200" />
```

**주의**: 첫 화면에 보이는 큰 이미지(대개 LCP 요소)에는 `loading="lazy"`를 붙이면 안 됩니다. 오히려 늦어집니다.

### 자리를 미리 잡기

```html
<img src="..." width="300" height="200" />
```

`width`/`height`를 주면 브라우저가 **이미지가 오기 전에 자리를 비워둡니다.** 24장의 CLS가 이걸로 해결됩니다. CSS로 크기를 조정하더라도 속성은 넣어 두세요 — 비율 계산에 쓰입니다.

> Next.js의 `<Image>` 컴포넌트는 크기 조정·포맷 변환·지연 로딩·자리 잡기를 한 번에 처리해 줍니다. Part 7에서 다룹니다.

## 폰트 — 작지만 눈에 띄는 문제

웹폰트는 크지 않은데도 체감에 영향이 큽니다. **글자가 안 보이거나, 보였다가 모양이 바뀌기** 때문입니다.

```
FOIT (Flash of Invisible Text)   폰트 올 때까지 글자가 안 보임
FOUT (Flash of Unstyled Text)    기본 폰트로 보였다가 나중에 바뀜 → 밀림(CLS)
```

**대응**

```css
@font-face {
  font-family: 'Pretendard';
  src: url('/fonts/pretendard.woff2') format('woff2');
  font-display: swap;        /* 일단 기본 폰트로 보여주고 나중에 교체 */
}
```

| `font-display` | 동작 |
| --- | --- |
| `swap` | 아주 짧게만 기다렸다가 기본 폰트로 보여주고, 나중에 교체. **글자가 거의 항상 보임**, 대신 교체 시 밀릴 수 있음 |
| `optional` | 잠깐 기다리고 늦으면 **이번 방문에서는 아예 안 바꿈**. 늦은 교체로 인한 밀림이 없음 |

> 한글 폰트는 글자 수가 많아 파일이 큽니다. **꼭 필요한 굵기만** 넣으세요. Regular와 Bold 둘이면 대개 충분합니다.
>
> 보통은 굵기 하나가 파일 하나입니다. 다만 **가변 폰트** 라는 형식은 한 파일로 여러 굵기를 냅니다. 굵기를 서너 개 이상 쓴다면 이쪽이 유리할 수 있습니다.

포맷은 **woff2** 를 씁니다. 다른 것은 거의 필요 없습니다.

## JavaScript

22장에서 다룬 이야기의 연장입니다. 확인 순서만 정리합니다.

1. **첫 화면 번들 크기를 잰다** — `next build` 출력, 또는 번들 분석 도구
2. **무거운 라이브러리를 찾는다** — 대개 하나가 범인입니다
3. **첫 화면에 필요한가 묻는다** — 아니면 지연 로딩(22장의 `import()`)
4. **더 작은 대안이 있는지 본다** — 21장의 선택 기준

**서드파티 스크립트를 특히 의심하세요.** 분석 도구, 채팅 위젯, 광고. 우리 코드가 아니라서 잊기 쉬운데 **크고 느린 경우가 많습니다.** 그리고 이들이 메인 스레드를 점유하면 INP가 나빠집니다(24장).

## HTTP 캐싱 — 두 번째 방문을 공짜로

여기서 백엔드 지식이 그대로 통합니다. 다만 **적용 대상이 다릅니다.**

### 두 가지 방식

```
Cache-Control: max-age=31536000   "1년 동안은 그냥 써도 돼"      ← 신선 기간
ETag: "a3f9c2"                    "이 파일의 지문은 이거야"        ← 확인용 딱지
```

둘은 대립하는 선택지가 아니라 **역할이 다릅니다. 같이 씁니다.**

- **신선 기간 안** — 요청이 아예 안 나갑니다. 캐시에서 바로 씁니다
- **기간이 지나면** — 브라우저가 `ETag` 값을 실어 서버에 물어봅니다. 안 바뀌었으면 `304`만 오고 본문은 안 옵니다

당연히 첫 번째가 훨씬 빠릅니다. 문제는 **"1년 동안 그냥 쓰라"고 했는데 내용이 바뀌면 어쩌나** 입니다.

### 해시 파일명이 이 문제를 푼다

23장에서 봤던 그것입니다.

```
main.a3f9c2.js    →  내용이 바뀌면 이름이 바뀐다
main.7b1e04.js    →  그래서 이건 다른 파일이다
```

**이름이 같으면 내용도 같다** 는 것이 보장되므로, 마음 놓고 영원히 캐시할 수 있습니다. 배포하면 새 이름의 파일을 받게 되니까요.

```
main.a3f9c2.js   →  Cache-Control: public, max-age=31536000, immutable
index.html       →  Cache-Control: no-cache
```

**`index.html`만 매번 확인하게 하는 것이 핵심입니다.** 이 파일이 "지금 어떤 해시의 JS를 쓸지"를 담고 있기 때문입니다. 진입점만 최신으로 맞추면 나머지는 전부 캐시에서 나옵니다.

> **`no-cache`는 "캐시하지 마라"가 아닙니다.** 저장은 하되 **쓰기 전에 서버에 확인하라** 는 뜻입니다. 정말 저장하지 말라는 것은 `no-store`입니다. 이름이 오해를 부르는 대표적인 헤더입니다.
>
> `immutable`은 **신선 기간 동안은 확인조차 하지 말라** 는 추가 지시입니다. 영구 보관을 보장하지는 않습니다. 브라우저는 공간이 필요하면 언제든 캐시를 버립니다.

### API 응답은 다른 문제

위 이야기는 **정적 파일** 이야기입니다. API 응답 캐싱은 성격이 다르고, 프론트엔드에서는 브라우저 캐시보다 **JS 안의 캐시 계층** 으로 다루는 것이 일반적입니다. 34장(TanStack Query)에서 본격적으로 다룹니다.

## CDN

정적 파일을 전 세계 엣지에 복제해 두고, 사용자에게 가장 가까운 곳에서 응답합니다. 리버스 프록시 캐시를 지리적으로 펼쳐 놓은 것입니다.

**서울 사용자가 서울 엣지에서 받는 것과 미국 원본 서버에서 받는 것은 왕복 시간이 수백 ms 차이납니다.** 요청은 병렬로 나가므로 개수만큼 곱해지지는 않습니다. 다만 **HTML을 받아야 JS를 알고, JS를 받아야 데이터를 요청하는** 식으로 서로 기다리는 단계가 이어지면, 그 단계마다 왕복 지연이 쌓입니다.

정적 호스팅 서비스(23장)는 대개 CDN을 기본으로 포함합니다.

## 연결 최적화 — 필요할 때만

브라우저에게 "이건 먼저 받아둬"라고 힌트를 줄 수 있습니다.

```html
<!-- LCP 이미지를 미리 받는다 -->
<link rel="preload" as="image" href="/hero.webp" />

<!-- 폰트 서버와 연결을 미리 열어둔다 -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
```

**남용하지 마세요.** 모든 것을 preload하면 우선순위가 사라져서 오히려 느려집니다. **LCP 요소 하나 정도** 에만 쓰는 것이 안전합니다.

## 진단 순서

```
1. Network 탭에서 크기 순으로 본다        ← 캐시 끄고 새로고침
2. 이미지부터 손본다                       크기 → 포맷 → lazy
3. 첫 화면 JS를 줄인다                     22장
4. 폰트는 필요한 굵기만 싣고, 늦은 교체를 허용할지에 따라 font-display를 고른다
5. 캐시 헤더를 확인한다                    해시 파일은 긴 max-age + immutable, html은 no-cache
6. 24장으로 돌아가 다시 잰다
```

## 흔한 오해

**"이미지는 CSS로 줄이면 된다"**
브라우저는 원본을 다 받은 뒤 줄입니다. 전송량은 그대로입니다.

**"모든 이미지에 `loading="lazy"`를 붙이면 좋다"**
첫 화면 이미지에 붙이면 LCP가 나빠집니다.

**"`no-cache`는 캐시하지 말라는 뜻이다"**
저장은 하되 "쓰기 전에 확인하라"입니다. 저장 자체를 막는 건 `no-store`입니다.

**"CDN을 쓰면 성능 문제가 해결된다"**
전송 거리만 줄여줍니다. 5MB 이미지는 CDN에서 와도 5MB입니다.

## 핵심 3가지

- **이미지가 대체로 가장 큰 범인입니다.** 표시 크기에 맞춰 줄이고, WebP로 바꾸고, 화면 밖 이미지만 지연 로딩하세요. 작업량 대비 효과가 가장 큽니다.
- **해시 파일명이 캐싱을 단순하게 만듭니다.** 내용이 바뀌면 이름이 바뀌므로 아주 긴 신선 기간을 줘도 됩니다. `index.html`만 매번 확인하게 하면 됩니다.
- **재고 고치고 다시 재세요.** Network 탭에서 크기를 보고, 고친 뒤 24장의 지표로 확인합니다.
