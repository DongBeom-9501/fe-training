# 4. 가상 DOM의 진실 — 빠른 게 아니라 예측 가능한 것

> **이 장의 질문**: "가상 DOM이 빠르다"는 말은 사실인가?

## 결론부터

**대체로 아닙니다.** 같은 결과를 내는 **최소한의** 직접 DOM 조작과 비교하면 가상 DOM은 일을 더 합니다. 그만큼 느립니다.

그런데 실제 앱에서 무엇이 더 빠른지는 작업량, 배칭, 실제로 바뀌는 DOM의 양에 따라 달라집니다. 이 장은 그 조건들을 정리합니다.

## BE로 치면 이런 것

ORM을 떠올려 보세요. Hibernate가 직접 짠 SQL보다 빠릅니까? 아닙니다. 엔티티를 추적하고, 더티 체킹을 하고, SQL을 생성합니다. 순수 오버헤드입니다.

그런데 우리는 씁니다. **직접 짠 SQL이 더 빠르지만 대부분의 경우 "충분히 빠르고", 그 대가로 일관성과 유지보수성을 얻기 때문입니다.** 그리고 정말 느린 지점에서는 네이티브 쿼리로 내려갑니다.

> ORM과 가상 DOM이 하는 일은 전혀 다릅니다. 한쪽은 SQL을 만들고 다른 쪽은 트리를 비교합니다. **닮은 것은 선택의 성격뿐입니다** — 손으로 최적화할 여지를 내주는 대신 일관된 모델을 사는 거래. 이 장을 읽는 동안만 쓰는 앵커라고 생각하세요.

## 가상 DOM이란 무엇인가

이름이 거창하지만 실체는 **평범한 JavaScript 객체** 입니다.

```tsx
<tr className="row"><td>ORD-1001</td></tr>
```

이 JSX는 컴파일되면 이런 객체가 됩니다.

```js
{
  type: 'tr',
  props: {
    className: 'row',
    children: { type: 'td', props: { children: 'ORD-1001' } }
  }
}
```

**이건 화면에 있는 게 아닙니다.** 그냥 메모리 속 객체 트리이고, "화면이 이렇게 생겨야 한다"는 **설명서** 입니다.

React가 하는 일은 이렇습니다.

```
1. 컴포넌트 함수 실행 → 새 설명서 생성
2. 이전 설명서와 비교 (diff)
3. 다른 부분만 골라서 실제 DOM에 적용
```

## 그래서 왜 느린가

수동 조작과 비교해 봅시다. 테이블의 한 셀 텍스트를 바꾼다고 하면,

```js
// 직접 조작: 정확히 필요한 일만 한다
cell.textContent = 'SHIPPED';
```

```
// React: 
컴포넌트 함수 실행 → 객체 트리 생성 → 이전 트리와 비교 → 차이 발견 → cell.textContent = 'SHIPPED'
└────────────────── 이 앞부분이 전부 추가 비용 ──────────────────┘
```

**마지막 한 줄은 똑같이 하고, 그 앞의 일을 더 합니다.** 이 비교에서는 빠를 수가 없습니다.

## 그럼 왜 쓰는가

세 가지 때문입니다.

### 1. "충분히 빠르다"

객체를 만들고 비교하는 것은 JavaScript 엔진이 아주 잘하는 일입니다. 반면 실제 DOM 조작은 레이아웃·페인트를 유발해서 훨씬 비쌉니다(입문 5장).

```
객체 트리 비교         :  싸다 (순수 계산)
실제 DOM 변경          :  비싸다 (레이아웃 → 페인트)
```

그래서 **"싼 계산을 더 해서 비싼 DOM 조작을 줄인다"** 는 거래가 성립합니다. 수동으로 짜면 대개 필요 이상으로 DOM을 건드리게 되므로(2장에서 목록을 통째로 지우고 다시 그렸던 코드), 실전에서는 React 쪽이 나은 경우가 많습니다.

다만 DOM을 고친다고 항상 레이아웃과 페인트가 도는 것은 아닙니다. 무엇을 바꿨느냐에 따라 다르고(입문 5장), 브라우저도 나름의 최적화를 합니다.

**정정하자면**: "가상 DOM이 DOM보다 빠르다"가 아니라, **"상태가 많은 화면에서 사람이 실제로 짜게 되는 DOM 조작보다는 나은 경우가 많다"** 가 맞는 문장입니다. 물론 정성껏 최적화한 수동 코드는 더 빠를 수 있습니다.

### 2. 예측 가능성 — 이게 진짜 이유다

수동 조작에서는 "지금 화면 상태 + 해야 할 변경"을 개발자가 계산합니다. 상태가 늘수록 경우의 수가 폭발합니다(2장).

가상 DOM에서는 **개발자가 "최종 화면"만 선언하고, 어떻게 도달할지는 React가 계산합니다.** 경우의 수가 사라집니다.

이게 성능보다 훨씬 큰 이득입니다. 성능은 나중에 튜닝할 수 있지만, 예측 불가능한 코드는 튜닝할 수도 없습니다.

### 3. 플랫폼에서 분리된다

설명서가 그냥 객체라서, 그걸 무엇으로 그릴지는 별개 문제가 됩니다. 같은 React 코드가 웹(react-dom)으로도, 네이티브 앱(react-native)으로도, 서버에서 만드는 HTML(SSR)로도 갈 수 있는 이유입니다.

> **서버 컴포넌트(RSC)는 SSR과 다른 축입니다.** SSR은 컴포넌트를 서버에서 HTML로 렌더하는 것이고, RSC는 아예 서버에서만 실행되고 클라이언트로는 내려가지 않는 컴포넌트입니다. 둘은 같이 쓰이지만 같은 것이 아닙니다. 24장에서 분리해서 다룹니다.

## diff의 규칙 — 어떻게 그렇게 빨리 비교하나

두 트리의 **최소** 차이를 정확히 구하는 알고리즘은 노드 수가 늘어날수록 비용이 폭발적으로 커집니다. 노드가 10배가 되면 연산은 1000배가 되는 식이라, 노드 1000개짜리 화면에서는 쓸 수가 없습니다.

React는 "최소를 정확히 구한다"를 포기하고, **어림짐작 규칙 두 개** 로 노드 수에 비례하는 수준까지 비용을 낮춥니다. 최적은 아니지만 충분히 좋은 답을 아주 빠르게 냅니다.

**규칙 1: 타입이 다르면 비교하지 않고 통째로 버린다**

```tsx
<div><Profile /></div>
// ↓ 바뀌면
<span><Profile /></span>
```

`div` → `span`이니 그 아래 `Profile`도 전부 파괴하고 새로 만듭니다. 안에 있던 state도 날아갑니다.

**규칙 2: 같은 레벨의 목록은 `key`로 동일성을 판단한다**

이게 6장 전체의 주제입니다. 지금은 "**`key`는 스타일이 아니라 diff 알고리즘의 입력값**"이라는 것만 기억하세요.

이 두 규칙 때문에 React는 **"트리 구조는 대체로 안정적이다"** 라고 가정하는 셈입니다. 같은 자리에 같은 타입, 같은 `key`가 유지되면 조건부 렌더를 해도 상태가 보존됩니다. 반대로 **자리·타입·`key` 중 하나라도 달라지면 그 컴포넌트는 새로 만들어지고 상태가 초기화됩니다.** 7장에서 구체적인 예로 다룹니다.

## Fiber — 렌더를 쪼갤 수 있게 만든 것

React 16부터 내부 구조가 **Fiber** 로 바뀌었습니다. 세부는 몰라도 되지만 **왜 바꿨는지** 는 알아둘 값어치가 있습니다.

이전에는 렌더가 시작되면 트리 전체를 다 돌 때까지 멈출 수 없었습니다. 트리가 크면 그동안 메인 스레드가 잡혀 있고, **화면이 얼어붙습니다** (입문 6장의 그 문제입니다).

Fiber는 트리를 **연결 리스트 형태의 작업 단위** 로 바꿔서, 중간에 멈추고 나중에 재개할 수 있게 만들었습니다. 그래서 이런 게 가능해졌습니다.

- 급한 업데이트(타이핑)를 덜 급한 업데이트(목록 필터링)보다 먼저 처리
- 렌더 도중 더 중요한 일이 오면 하던 렌더를 **버리고** 다시 시작
- `useTransition`, `Suspense` 같은 기능

**"버리고 다시 시작"이 가능하려면 렌더가 순수해야 합니다.** 3장의 계약이 왜 필요한지가 여기서 드러납니다.

## 그래서 React는 언제 느린가

가상 DOM 자체는 병목이 아닙니다. 실무에서 느려지는 지점은 거의 항상 이 셋입니다.

| 원인 | 설명 | 어디서 |
| --- | --- | --- |
| **불필요한 리렌더** | 안 바뀐 컴포넌트까지 함수가 다시 실행됨 | 7장 |
| **렌더 안의 무거운 계산** | 매 렌더마다 큰 배열을 정렬/필터 | 13장 |
| **한 번에 너무 많은 DOM** | 수천 행을 한꺼번에 그림 | 20장 |

**세 가지 모두 "가상 DOM이 느려서"가 아니라 "일을 너무 많이 시켜서"입니다.** 그래서 최적화의 방향도 "React를 걷어내자"가 아니라 "일을 줄이자"입니다.

## 가상 DOM 없는 대안들

Svelte, Solid 같은 프레임워크는 **컴파일 시점에 어디를 바꿔야 할지 계산해서** 가상 DOM 없이 직접 DOM을 갱신합니다. 여러 벤치마크에서 좋은 성적을 냅니다(어떤 작업을 재느냐에 따라 결과는 달라집니다).

React도 컴파일 시점의 도움을 받는 방향을 받아들이고 있습니다. 다만 **React Compiler**(22장)는 가상 DOM을 없애는 것이 아니라, 불필요한 재계산과 리렌더를 줄이는 최적화를 자동으로 넣어 주는 것입니다. "가상 DOM이 정답이다"가 아니라 **"현재 시점의 트레이드오프"** 라고 이해하는 게 정확합니다.

## 흔한 오해

**"가상 DOM이 DOM보다 빠르다"**
느립니다. 대신 사람이 대충 짠 DOM 조작보다는 빠른 경우가 많고, 예측 가능성을 줍니다.

**"React는 바뀐 것만 다시 렌더한다"**
아닙니다. **바뀐 것만 다시 DOM에 반영합니다.** 렌더(함수 실행)는 훨씬 많이 일어납니다. 이 구분이 5장과 7장의 핵심입니다.

**"diff가 최적의 차이를 찾아준다"**
휴리스틱입니다. 최적이 아니라 "충분히 좋고 빠른" 답을 냅니다. 그래서 `key`가 필요합니다.

**"성능이 걱정되면 memo를 붙이면 된다"**
`memo`도 비용이 있습니다. 13장에서 언제 해로운지 다룹니다.


측정하지 않은 최적화는 대개 코드만 복잡하게 만듭니다. **Profiler로 먼저 재세요**(21장).

## 핵심 3가지

- **같은 결과를 내는 최소한의 수동 DOM 조작보다는 느립니다.** 일을 더 하니까요. 대신 사람이 실제로 짜는 코드보다는 나은 경우가 많습니다.
- **진짜 이득은 예측 가능성입니다.** 최종 화면만 선언하고 도달 경로는 React가 계산합니다.
- **느려지는 원인은 가상 DOM이 아닙니다.** 불필요한 리렌더, 렌더 중 무거운 계산, 한 번에 너무 많은 DOM. 셋 다 "일을 줄이는" 방향으로 해결합니다.
